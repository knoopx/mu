# mu — working notes

A GPU-rendered desktop client for the pi coding agent: `@gpuix/react` + `adwaita-gpuix`, no DOM, React 19, TypeScript strict, bun.

## Commands

- `bun run dev` — the app, hot (`bun --hot app.tsx`)
- `bun run typecheck` — `tsc --noEmit`; the tree is expected to stay clean
- `bun storybook .` — renders every scene in `README.md` to `stories/<Feature>/<story>.png`

## Layout

Each plugin is one folder under `src/plugins/`, and every plugin is built the same way inside: `lib/` for logic with no JSX, `components/` for what is drawn, `hooks/` for files whose export is a hook, `tools/` for the agent tools it registers, and `types.ts` and `constants.ts` at its root for what the whole plugin shares.

```
src/plugins/
├── core/            the app itself: registers no tool of its own, and adds screens/ for what fills the window
│   ├── lib/         agent/ codemode/ commands/ composer/ files/ project/ session/ theme/ ui/ utils/ workspace/
│   ├── components/  transcript rows, composer panels, project card, session tree
│   ├── hooks/       useChatSession, useSessionTree, useThemePanel, useWorkspaceStatus, ...
│   └── screens/     Chat.tsx
├── code-quality/    lib/ (cli/ fallow/ json/ review/ answer/ params/ toolView/) components/ tools/ types.ts constants.ts
├── interaction/     lib/ components/ hooks/ tools/askUser.ts types.ts constants.ts
├── guardrails/      lib/ (treeSitter/ rules/ rulesFile/ engine/ store/ panelRows/ coverage/ report/) components/ hooks/ tools/ README.md types.ts constants.ts
├── vcs/             lib/ components/ hooks/ tools/ types.ts constants.ts
├── web-search/      lib/duckduckgo/ components/ tools/webSearch.ts types.ts constants.ts
├── openui/          lib/ (programStore/ analysis/ answer/ params/ schema/ toolView/ format/ tokens/ theme/) components/ (library/) hooks/ tools/ README.md types.ts constants.ts
├── mermaid/         lib/ (diagram/ palette/ answer/ toolView/) components/ tools/mermaidRender.ts types.ts constants.ts
├── figures/         lib/ (plot/ structure/ answer/ toolView/) components/{Chart,Tree,Table}ToolRows.tsx tools/{chart,tree,table}Render.ts types.ts constants.ts
├── github/          lib/ (api/ client.ts record.ts read.ts, call/ answer/ params/ toolView/ reader.ts) components/ tools/ types.ts constants.ts
├── planning/        lib/ (steps/ answer/ toolView/) components/PlanToolRows.tsx tools/plan.ts types.ts constants.ts
├── terminal/        lib/ (pty/ screen/ palette/ paint/ keys/ geometry/ session/ shortcuts/) components/TerminalPanel.tsx hooks/useTerminalPanel.ts types.ts constants.ts
└── snapcompact/     lib/ (load/ config/ reader/ archive/ plan/ replay/ note/ extension/) types.ts constants.ts README.md
```

A namespace is a folder inside a kind: the agent bridge is `core/lib/agent`, the composer's layout and mode logic is `core/lib/composer`, the DuckDuckGo engine is `web-search/lib/duckduckgo`, the OpenUI component library is `openui/components/library`. A tool is one file per tool, named after the tool: `interaction/tools/askUser.ts` is `ask-user`, `web-search/tools/webSearch.ts` is `search-duckduckgo`, `guardrails/tools/guardrailsTest.ts` is `guardrails-test`, `vcs/tools/vcsLog.ts` is `vcs-log` — the file is camelCase, the tool name it registers is kebab. A plugin that registers no agent tool has no `tools/`.

### Imports: no barrels

Nothing under `src/plugins/` re-exports a folder, and there is no `index.ts` in any plugin or namespace. Every import names the file it comes from: `../../core/lib/ui/theme`, `../../lib/composer/panelHeight`, `../../../interaction/tools/askUser`. Crossing into another plugin means naming that plugin's file — `core/lib/agent/agentService.ts` registers the ask tool by importing `../../../interaction/tools/askUser`, and `core/lib/project/projectSummary.ts` reads jj through `../../../vcs/lib/repo`.

Adding a file means adding its path at each consumer; there is no public surface to keep in sync, and moving a file updates only its own consumers.

### Naming

- a component file is PascalCase and matches the component it exports (`vcs/components/ChangesPanel.tsx` exports `ChangesPanel`). The one exception is a namespace of component *definitions* rather than components: `openui/components/library/layout.tsx` holds the `Stack`, `Row` and `Grid` definitions of one area of the language and `registry.ts` registers them — the area is the unit there, not one component
- a hook file is `useThing.ts` and lives in its plugin's `hooks/`, in the plugin that owns the thing (`useProjectSummary` in `core/hooks`, `useChangesPanel` in `vcs/hooks`)
- a namespace keeps its key hints in `shortcuts.ts`, and a plugin keeps what the whole plugin shares in `types.ts` and `constants.ts`
- when two modules in one namespace want the same name, the name is the thing that is wrong: the changes panel's state hook returns `ChangesPanelState` so the `ChangesPanel` component owns the name, and the composer counts rows in a height with `composerPanelRowsForHeight` so the panel's own `composerPanelRows` owns its name

## Stories

One feature, one story, one scene. Each story in `stories/` renders the app — the window, the log, the composer slot, the status bar — at the size the real window is used at, with a session in it doing the thing the feature is. A story is a picture of the app being used, not a component in a box.

**A scene carries its own conversation.** The scene behind a feature is the feature's evidence, so `Chat/session` showing the same log as `Paths/completing` says nothing about either: every feature writes its own transcript in `.storybook/fixtures/scenes/<feature>.ts` — its own prompts, its own tool calls, its own answer — and no two images the README shows may share one. `scenes/photo-strip.ts` is the hero and the only transcript that appears twice (the `Chat/session` window, and the preview pane of `Sessions/list`, which is previewing *another* session on purpose); `scenes/looks-rules.ts` carries the theme-picker shot and `scenes/looks-accent.ts` the accent-picker shot: `Looks` is two screens, not one screen in four themes, because four renders of one transcript and one panel are one image repeated. `bun .storybook/checkUnique.ts` grades this — a story is its transcript, its open panel and its theme stage, and two stories sharing all three (or one transcript between them, `photo-strip` excepted) fail the run. A scene's rows are built with `userTurn/ran/failed/running/answer/usage` from `fixtures/turn.ts`, its command output lives beside it, and its figures are read at the scene's own `clockOf` moment so the PNG is the same PNG every capture. The PNG it writes is the image `README.md` shows for that feature, so every heading in the README has a scene behind it and every scene has a heading.

**The README is a gallery and nothing else:** `# mu`, one `##` per feature, one image per story. No intro, no captions, no keymap, no capture or build detail — not one sentence of prose. What a screen shows is carried by the heading, the story name in the image path, and the pixels; anything worth explaining becomes another story, and every other kind of sentence belongs in this file.

- `bun storybook .` renders every scene to `stories/<Feature>/<story>.png`
- `bun storybook . --only Chat` renders one feature
- the capture keeps the declared window width and fits its height to what is painted, so heights are a starting point, not a promise
- fixtures live in `.storybook/fixtures` and are shared between features: transcript scenes in `scenes.ts`, tool rows in `tools.ts`, project history in `project.ts`, conversation trees in `tree.ts`, pasted images in `images.ts`
- the window-scale helpers live in `.storybook/chrome`: `chat()` puts a session in the window, `askInChat()` puts a question in the composer slot, `overChat()` opens an overlay over the log

A story id is the meta `title` over the exported scene, so `stories/Chat.stories.tsx` with `title: "Chat"` and `export const session` is the `Chat/session` scene, and it writes `stories/Chat/session.png`.

One feature, one story — the only feature with two is one whose stories open different panels (`Models`: the model list and the thinking levels; `Changes`: the change stack and the operation log) and `Looks`, which is one session under four themes.

**One story per screen, and no story repeats another's screen.** A story is the transcript in the log plus the panel open above the composer plus the theme painted under it; two stories with all three are one image twice, and one transcript across two panels is how 12 of the 20 README images ended up being one conversation with a different panel bolted on. `bun .storybook/checkUnique.ts` grades that — it reads every `stories/*.stories.tsx`, and exits 1 naming any pair that shares a screen, or shares a transcript under the same panel and theme (the `Looks` row is one session in three themes on purpose; `Sessions/list` previews the hero's session, being a preview of *another* session).

Thirty-one stories cover every plugin the app registers and all 31 have a captured PNG (captured 9 Nov, one run, `31 ok, 0 failed`). The README shows eleven of them, so the gallery is the part still short — a story without a README heading is a feature the reader never sees, and `grep -c 'stories/.*\.png' README.md` against `bun storybook --dry-run` is the count that says so.

A stale PNG is worse than no PNG. The eight stories above marked `no` that once had pictures (`Composer/drafting`, `Paths/completing`, `Models/model`, `Models/thinking`, `Sessions/list`, `History/tree`, `Changes/panel`, `Questions/asked`) were captured on 8 Nov, before their scenes were rewritten, so those PNGs showed the hero's photo-strip session; they have been deleted rather than left to lie, and the README shows only the eight images that are genuinely distinct screens. The features whose tools live in the log and not in a panel (web search, code quality, documents-as-an-answer) have no story of their own: their rows are already in `Chat/session` and `AgentActions/work`, and a second full-log screen would be a duplicate. **Capture is offscreen and maps no window**, measured on this machine on 9 Nov: `niri msg windows` counted 7 windows before a capture run and 7 after it, the run wrote 31 PNGs, and a picture is real content (`identify`: 720x1080, mean 0.38, stdev 0.08 — not a black frame). No `ZED_HEADLESS` is set and none is wanted. What capture needs is a binding that *loads*, which is a library problem, not a platform limit: the local `@gpuix/native` build's RUNPATH named seven GC'd store dirs (`ldd` with `LD_LIBRARY_PATH` unset answered `not found` for `libxcb`, `libfontconfig`, `libfreetype`, and napi then silently falls back to the npm stub whose message reads "TestGpuixRenderer is macOS and Windows only"), and the `NAPI_RS_NATIVE_LIBRARY_PATH` mu's wrapper exports points at a build without `test-support`. `storybook/src/lib/gpuix-rpath.ts` repairs the artifact — a git-ignored `.gpuix-libs/` of symlinks to the live store copies (the `NEEDED` list plus the runtime `dlopen`s: wayland, vulkan, EGL) and an in-place, byte-exact RUNPATH rewrite naming it — and `pinTestBinding` in `storybook/src/cli.ts` overwrites that env pin with the local `test-support` build. **Any older sentence in this file claiming capture needs a compositor, maps a window per story, or must run against a compositor with no output was written against an unpatched gpuix and is wrong for this fork** — including the storybook README's former "Linux capture is not headless" bullet, which has been corrected the same way. There is still no `stories/StatusBar.stories.tsx`: the bar is only ever seen inside the other scenes, and the `Chat/session` shot is where its figures are shown.

## Notes

- Path completion lives in `core/lib/composer/pathCompletion.ts`: the draft's trailing path token (`~`, `~/x`, `/x`, `./x`, `../x`, `@x`, anything with a `/`) is listed as a shell lists it, and the completion panel's query **is** the draft — `isCompletionMode` — so typing keeps editing the draft and Tab takes the highlighted path, a directory keeping the panel open. Tab is `editor.autocomplete`, handled in `composer/keyRouter.ts` with the `cycle` flag so the window listener never takes a completion twice. **Tab completes, Enter commits**: `pickActive(intent)` carries a `PickIntent` (`lib/composer/mode.ts`) through `ComposerPanelSpec.onPick` into `panelActions.pickPanelRow`, and path completion is the only panel that reads it — Enter on a folder writes the path and dismisses the panel, Tab keeps completing inside it, and a row's mouse click completes exactly as Tab does. **A panel is a choice, never a send**: `panelListKeys`'s `onEnter` is that commit and `ComposerField.onSubmit` picks whenever a panel is open, so path completion can never submit the draft to the conversation. With no name to take, Enter is inert; Escape closes the suggestions and leaves the characters typed, and Enter in the draft then sends them. `pathCompletionShortcuts` prints Tab's `complete` beside Enter's `use`.
- There is no DOM. Style objects are `StyleDesc` values and layout is flex; `adwaita-gpuix` owns theme tokens, and colour helpers live in `core/lib/ui/theme.ts` so a component never hand-mixes a hex.
- No component writes a bare number in a style. `core/lib/ui/tokens.ts` is the one answer to how big, how much space, what leading and what weight, and it defers to adwaita's scale where that scale already owns the value: `ROW_HEIGHT` is the height of every one-line row (the tree, a change feed, a picker), `monoColumn(t, chars)` *budgets* a column of monospace text and `monoTextWidth(t, chars)` measures what that text actually prints (`idColumn(t)` is the log's own column, budgeted), and `figureGap(t)` is the one role-gap the scale cannot name — the air between the figures a row trails, which five files used each to spell as `t.space.sm` on their own; `lineBox(t, role)`/`codeLineBox(t)` are the line boxes of text roles (`leadingOf` for a caller that sets a ratio), `emphasisWeight(t)`/`titleWeight(t)`/`plainWeight(t)` are the only weights, `MARKER_GLYPH`/`INLINE_GLYPH`/`STATE_GLYPH`/`ACTION_GLYPH` are the marks a row draws (`STATE_GLYPH` is the log's mark — a header glyph, a running spinner, a note's icon — and `MARK_HANG` how far it hangs into the page inset), `HAIRLINE` is every rule and edge, and `elevatedShadow()` in `theme.ts` is the one drop over the log, from `ELEVATION`. A plugin's own sizes stay named in its own file when nothing else asks for them (`MAX_ROWS`, `PANE_GROW`); what must not happen is two files spelling the same number differently. Secondary text is `mutedText(t)` — a call site never reads `t.color.text.dim`.
- The transcript page inset (`PAGE_INSET` in `core/lib/ui/transcriptLayout.ts`) is one constant imported everywhere; the adwaita tool-header glyph hangs 24px into it, so the inset stays at 56. The gutter of marks runs the whole height of the window: a running session is a `STATE_GLYPH` spinner hung the same `MARK_HANG` beside the composer box (`ChatComposerSlot`), not a line of prose at the end of the log. That mark is one component, `core/components/StateSpinner.tsx`, and it turns pi's own frames — the ten braille cells of pi's `Loader` (`DEFAULT_FRAMES`), one every 80ms (`DEFAULT_INTERVAL_MS`), in the accent tone — so a running session looks the same here as in the terminal; adwaita's ring `Spinner` is not used anywhere in mu, and the one place it would reach the screen unasked is a running tool header's trailing mark, so `ToolExecution` hands adwaita's `ToolHeader` a `spinnerSlot` of `StateSpinner` and the header keeps only its settled check icon (`spinnerSlot` is the library's own escape: `StatusGlyph` draws whatever the app gives it while it runs, and its icon when it does not); the cell is set in the mono family because that is the family with braille coverage, and `STATE_GLYPH` is adwaita's `GUTTER_GLYPH`, so a header's trailing column does not move when the mark changes — there is no "Working" row and no loader in the transcript. The box keeps the exact x and width it had a moment before because the mark's row pays back the width the hang takes (`MARK_HANG - STATE_GLYPH` of margin), and the mark stands in that row rather than inside the composer's own root, whose fill clips its children.
- The log is a two-column grid and `core/lib/ui/toolRows.ts` owns it: **text** of every row — a header title, an answer's caption, a preview line, a system row — starts at `PAGE_INSET`, and every **mark** hangs `MARK_HANG` to its left, in `STATE_GLYPH`, because adwaita's `ToolHeader` puts its glyph there (`GUTTER_GLYPH`/`GUTTER_GLYPH_HANG`, neither exported) and nothing else in the log gets to pick a second column. So `toolColumn`/`toolGapColumn` open with `paddingLeft: 0` (a column that padded its own left edge indented every body line away from the head it answers), a row-leading icon takes `style={toolMark}` (`toolMarkIn(padding)` inside a column that really does pad), and a lone note is wrapped in `toolBodyStack` rather than returned bare. A plugin never hand-rolls an icon-plus-caption line: `ToolStateLine` (`ToolStateNote`/`ToolStatusNote`) and `ToolCaptionLine` are the only two, and they take `toolText(t)`, which puts a log line on `lineBox(t, "caption")` leading while `toolLine` keeps the row at least that tall — otherwise the rows of an answer sit tighter than the prose above them.
- **A panel closes on the choice it was opened for.** The jump-back tree's Enter goes through its own `wideKey` (`useSessionTree.onKey`) into `useChatPanels.jumpTree`, which navigates and sets `draftMode()` in the same breath: a wide panel draws no draft field (`WIDE_SLOTS`), and a jump back over a user node writes that node's text into the composer, so a panel left open would hide the very draft the jump handed back. The guardrails panel is the deliberate exception — arming is a switch, so its row stays put — and the two repo panels keep their own keys and their own writes.
- **One delete key, and the panel says what its row is.** `composer.deleteRow` (Delete) is matched once in `composer/keyRouter.ts` and answered by `composer/panelActions.ts:deletePanelRow`, which reads the open panel's target; `composer/shortcuts.ts` keeps the one list of panels that can delete (`DELETABLE_PANELS`) and `panelShortcuts` prints the hint for exactly those, so a hint a panel does not print is a key that panel does not take. The session panel hands its row to pi's session store; the file panel hands its row to `lib/files/deleteFile.ts`, which takes a name that stays inside the folder and refuses a folder or a name that walks out of it. `lib/files/` is the file panel's whole read: `fileList.ts` walks the project once per folder, `fileIcons.ts` names the row, `filePreview.ts` reads the pane, and `hooks/useFileList.ts` drops the walk when a delete lands, so the row that just went cannot sit in the list previewing nothing.
- Every panel in the composer slot — the draft's list panels, the question panel, the changes panel, the history panel — is framed by `core/lib/composer/chrome.ts`, and nothing else states their padding. `panelBox(t, tone)` is the band, and it pads itself by one unit — `panelPad` (`space.sm`) on **all four** sides, so `panelPageInset` and `panelPadY` are the same number and a panel breathes equally top, left, bottom and right. Everything the panel says then stands `panelInset` further in, so the ink column sits at twice the band's breathing from the left and right and one measure from the top and bottom — a 1x2 width-to-height ratio, an equal band being its degenerate case, and the reason a second padding number in a panel is a bug rather than a taste (a chip or an inline mark is not a band and keeps its own measure). The field, the list, the hints line and the notes all stand in that one column, and a row's hover band simply runs `panelInset` wider than its text. `panelChrome(t)` owns the panes (`listPane`, `flexPane`, `widePane`, `previewPane`, `previewCode`), the rules (`ruleV`/`ruleH` take the colour a panel's tone asks for, since tone is the one thing chrome cannot know), the `rowSlot` a virtual list stands one row in, and the `emptyPane`; `ChangesPanel`, `SessionTreePanel` and `AskComposer` all read it rather than restating it. `panelHeight.ts` does the arithmetic over those same numbers — `panelChromeHeight(t, slots)` charges a panel only for the slots it draws, and the wide panels draw no draft field — so a padding moved in `chrome.ts` moves a row budget with it. `lib/composer/field.ts` is the one answer for the draft every panel types into: `panelInset` of left padding and `fieldPadY` of breathing (floored, so a one-row field plus its pad stays inside `ROW_HEIGHT`), whether it holds one line (`composerFieldLineStyle`) or grows with its text (`composerFieldBox`). `paneInk(t)` is the padding of the ink a pane holds that is *not* a row — the preview pane (`previewPane` pads itself with it, so adwaita's `DiffPanel`, mu's `previewCode`, an image tile's caption and a pane note all land under the file paths above them), the question panel's title, context, detail and hint row. `panelGap` is the air between one panel's slots and `paneGap`/`ruleGap` are exactly twice it, so nothing writes `t.space.md` between two panes.
- The figures the status bar keeps in view are the **session's own, read live**. `core/lib/agent/turnStats.ts` is the only place they are computed: one `scan` over the log's rows answers what the provider has reported, what is still streaming, and when the rows last did something, and `conversationStats(items, clock, sessionStart?)` folds that into the bar's turns, tokens, span and rate — a span from the log's first timestamped row to its last activity, never from when the window opened, so a resumed session says its own length and a new one starts at zero. `useRunningClock(running)` (`core/hooks/`) ticks `now` while a run is in flight and `Chat.tsx` hands it to `useTranscriptView` as a `SessionClock`, so elapsed time keeps moving through the seconds a turn spends in its tools, where nothing streams. A decode in flight has no usage to read — a provider answers at the end of a message — so its tokens are *estimated* at four characters each, the estimate pi's own compaction makes, and the row carries the timing for it: an assistant row keeps `startTs` from `message_start` and a tool row `endTs` from its result, so the live figure counts streamed prose, reasoning, and the arguments of the calls the streaming message is still writing, and never the arguments of a call that already ran (its tokens landed in a usage figure). `ConversationStats.live` says the rate is being measured now, and the bolt segment stands in the accent while it is. Turn footers stay settled-only: `turnStatsById` answers a turn's figures with no estimate, because the moving numbers belong to the bar. `ChatAppProps.now` pins the clock for a story — `.storybook/fixtures/turn.ts`'s `clockOf(items)` puts a scene's moment a moment and a half past its last row — so a scene with a running turn captures the same PNG twice.
- Images go through pi's own pipeline and `core/lib/agent/settings.ts` overrides nothing in the `SettingsManager` it builds for `createAgentSessionServices`: an image is converted to a supported format, EXIF-corrected and downscaled under the provider's inline limit, and the note pi adds tells the model the coordinate scale. Every resize path reads `photon_rs_bg.wasm` **from disk** — the resize worker cannot start from an embedded bundle, and photon's glue asks for the build machine's path — so a `bun build --compile` binary resizes only if the package installs that wasm where pi's loader already looks, beside the executable (`flake.nix` puts it in `$out/lib/`). Without it `resizeImage` returns null and every image answers "[Image omitted: could not be resized below the inline image size limit]", at any size. There is no `images.autoResize` override: an in-memory `applyOverrides` is wiped by pi's `SettingsManager.reload()` during resource loading, so it was inert anyway.
- **A wrapper's environment is mu's, never a child's.** The Nix wrapper sets `NAPI_RS_NATIVE_LIBRARY_PATH` (gpuix-native's `.node` under `$out/lib`) and `NODE_PATH` (`$out/lib/node_modules`, where QuickJS's wasm ships) because a `bun build --compile` executable finds neither on its own, and a wrapper cannot give one process an environment of its own. So the app retires them itself, in `core/lib/utils/loaderEnv.ts`: `retireNativeLibraryEnv()` runs in `app.tsx`'s entry body — after the entry's own imports have loaded the GPU binding, which is the only thing the variable is ever for — and drops it from `process.env`, the environment pi's bash tool and every other spawn inherits; `withoutMuLoaderEnv()` strips both at the spawns mu owns that are not mu (the pty shell, the analyser CLI, the editor), and `withMuLoaderEnv()` hands them back to a child mu window. That is not tidiness: every napi-rs generated loader — gpuix-native's own `index.js`, and the same generated file in `@tailwindcss/oxide`, tree-sitter, oxc — reads that variable before it looks anywhere else, `require`s what it names, and never checks what came back, so a project built inside mu loads gpuix-native as its own binding and dies somewhere else on an export that is undefined. `NODE_PATH` cannot be retired the same way, because pi resolves `quickjs-wasi/quickjs.wasm` through it lazily at the first codemode call; it is stripped per spawn instead.
- The **local `@gpuix/native` build carried its own library answers in its ELF RUNPATH**, and all seven of them named a GC'd `gpuix-build-env` output: `ldd` answered `not found` for `libxcb`/`libfontconfig`/`libfreetype` and the napi loader fell back to the npm stub, whose message reads "TestGpuixRenderer is macOS and Windows only". `storybook/src/lib/gpuix-rpath.ts` repairs the artifact instead of the environment — a git-ignored `.gpuix-libs/` of symlinks to the live store copies (the `NEEDED` list plus the runtime `dlopen`s: wayland, vulkan, EGL, which sit in packages no soname predicts) and an in-place, byte-exact `RUNPATH` rewrite naming it. Measured: `ldd` with `LD_LIBRARY_PATH` unset reports nothing missing, and `hasTestGpuixRenderer()` is true with no environment set at all. The RUNPATH write is guarded — offset past the ELF header, the bytes at that offset must equal the string read there, and the replacement must be exactly as long — because a wrong offset overwrites the magic bytes of an 812 MB artifact, which is what happened once; `cp` from a backup restores it, and the hardlinked `.bun` copies follow the inode.

A `Query(name)` has no backend but the JSON `openui-tools` served, and an unserved name **fails open** — the failure is published to the program and `openui-state` prints it rather than showing an empty table.
- figures is three tools — `chart-render`, `tree-render`, `table-render` — and those names are what a user's guardrail rule points at, so they are never renamed. `FIGURE_TOOL_NAMES` is the plugin's own list (it is what `APP_TOOL_NAMES` splices); the row predicates are per tool, `isChartTool`/`isTreeTool`/`isTableTool`, because one call is painted by one set of rows and a predicate that answers for all three would send a tree to the chart. it reads the points a tool call sends as typed JSON *and* the points a program's `Chart` writes as source text, and it owns the series names, the point cap and the measure (axis span, range, total, mean, peak). A tone stays a word and the series ramp is resolved **at paint time**, so a plot travels in `details` as data and never as a bitmap — which is why re-theming redraws a chart and a resumed session still draws one, unlike an openui program. `openui/components/library/data.tsx` reads that file instead of keeping its own coercion (its `CHART_*` geometry moved to `figures/constants.ts`), so a program's plot and a tool's plot cannot drift; the one thing that differs is what a caller does with a value that is not a number, because only one of them can answer back: the tool refuses the whole call and names the point the cell sat on, a drawer draws what it could read. The model never sees the plot: `lib/answer.ts` gives it a reading — points plotted, the axis, range, total, mean, peak, and the points as figures, `…N not shown` past the readout budget and `…N not plotted` past `MAX_POINTS`, which is the sign to group the values. `components/ChartToolRows.tsx` paints `AdwaitaChart` and the `ChartLegend` a multi-series plot needs — adwaita exported the legend and nothing drew it, so a program's series were unnamed colours named `s1`.
- `lib/structure.ts` is the **second contract**, sibling of `plot.ts`, for the two shapes that are not plots: a tree of named nodes and a table of cells under a header. It reads what a call wrote *loosely* and refuses what it cannot mean: a bare value in a `children` slot is one child (the openui `listProp` lesson, applied before a drawer can crash on it), a row may be a list of cells or an object keyed by the column names, a missing header is derived from the first object row or counted positionally — but a node with no name, or a cell with no column to stand in, answers `invalid` and names the path or the row, and the whole call is refused rather than drawn short. Caps are the contract's too: `MAX_NODES`/`MAX_DEPTH` cut branches and `MAX_ROWS` cuts rows, and the answer says how many fell off. A tree is painted by adwaita's own `FileTree` (`variant: "list"`, `defaultExpandedPaths` from the figure, so its folders still open under the cursor in the log) and a table by adwaita's `Table`, with a column of figures set in mono and right-aligned — the same reading `openui/components/library/rows.ts` gives a program's `Table`, which is why the column's `figure` flag is decided in `structure.ts` and only *painted* by the component. **There is one table in the app:** `TableToolRows` and the openui `Table` drawer both draw `<Table density="compact" frame="bare">`, because a row of a table is one line of text (adwaita's `rowHeight` 24 is core's `ROW_HEIGHT`) and a table read in the log or inside a pane stands on that page, divided by its rules alone — the `frame` prop is the library's, and a second implementation built from divs and `HAIRLINE` rules is exactly how the two drifted apart. The header band is the library's measure too (`headerHeight`, never the row's height) and its rules wear `divider.default` like every other rule in the log, while the box around a *framed* table stays `border.default`. What the model gets back is the shape as text: `treeLinesOf` walks the tree as indented lines, `tableRowsOf` hands `tableOf` one record per row, and `tableFigureLinesOf` states each numeric column's Σ and range — so a leaf one level too deep, or cells that went into the wrong columns, is visible without eyes.
- github is nine tools — `github-repo`, `github-file`, `github-tree`, `github-pr`, `github-issue`, `github-release`, `github-commit`, `github-search`, `github-user` — and those names are what a user's guardrail rule points an agent at, so they are never renamed or aliased. They are the port of the `github-fetch` skill from `~/.pi`, split into one tool per thing instead of one tool that guesses a kind out of a URL: a URL parser leaves the model guessing which of two shapes a path has, and the answer text then has to say it back. There is no CLI: **`lib/api/client.ts` is the only file that names a host**, and it reads `https://api.github.com` (and `raw.githubusercontent.com` for a file the contents endpoint refuses) with `fetch`, signed by `GITHUB_TOKEN`/`GH_TOKEN` when the environment holds one. It owns the timeout, the reply status (`ok`/`failed`/`unsupported`), the wording of an HTTP refusal (`not found: <path> — no such repository, ref, path, number or tag`, the rate-limit note, the token hint) and the **24h cache under `$XDG_CACHE_HOME/mu/github`** (`muCacheDir` in `core/lib/utils/paths.ts`); `refresh` is the parameter that skips it. A read never builds answer text and the view never parses HTTP: `lib/api/read.ts` turns one endpoint into one `GithubCall`, `lib/call.ts` is the single writer of that envelope (`blankCall` then `answered`, so a failure carries the same shape as a success), `lib/api/record.ts` is the only reader of GitHub's JSON and never trusts it, `lib/answer.ts` writes the model's tables (a record as `field / value`, a list in its kind's own columns, a body after them raw), and `lib/toolView.ts` is the only reader of `details`. One envelope and one view for all nine is deliberate: `GithubCall` is fields + rows + body whatever the kind, so `components/GithubToolRows.tsx` is one component and `lib/reader.ts` is the `execute` body they share. `GithubCall.status` is `ok`, `empty`, `failed`, `unsupported` or `binary` — `binary` is a file whose bytes are not text, `unsupported` is no network or a signed-in read (code and commit search) without a token, and the last is answered before the request is made rather than as a 401. Every list is capped in `constants.ts` and the answer counts what fell off.
- mermaid is one tool, `mermaid-render`, and that name is what a user's guardrail rule points at, so it is never renamed. `lib/diagram.ts` is the only file that names the engine (Pele, pure JS: it measures text from its own metrics, so it needs no DOM and ships no runtime asset); it answers in one status vocabulary — `ok`, `failed`, `empty` — and a parse failure arrives as `code`/`line`/`column`/`snippet`, never as a thrown parser error. `lib/palette.ts` is the only place a diagram's colours are decided: Pele emits `var(--pele-*)` roles and leaves every `<text>` element unstyled (it expects a stylesheet it never ships), so the roles are resolved against the app's theme and each text node is told its font, size and fill **at paint time**, in the row — which is why the raw SVG markup travels in `details` and `components/MermaidToolRows.tsx` draws the picture rather than the tool. **A diagram gets no page of its own**: Pele draws no canvas-covering rect and the `<img>` gets no `backgroundColor`, so the ink stands on the log like a row of prose does. That makes the log's page — `paneFill(t)` from `core/lib/ui/theme`, not a surface of the plugin's choosing — the answer for `--pele-bg` (the plate under an edge label) and `--pele-surface` (a node's interior, a gantt section band): those shapes exist only to cover what passes behind them, and any *other* colour there turns the picture into a darker card with holes punched in it. Grouping is the one thing that does get a fill, `surface.hover`, and Pele already paints a subgraph band at `fill-opacity .5`, so it tints the log instead of hiding it. The model never sees the picture: `lib/answer.ts` gives it a reading instead — the kind, the canvas, and every label the diagram says — and a missing label is how a wrong source is caught. There is deliberately no rasteriser: `@resvg/resvg-js` is a NAPI binary whose loader would read the one `NAPI_RS_NATIVE_LIBRARY_PATH` the wrapper sets for `@gpuix/native` — it needs its own loading path, not just a dependency — and the picture is a vector the log scales into `DIAGRAM_BOX_*` anyway. `path` writes the `.svg` (full size, no scaling) so a diagram can be committed.
- planning is one tool, `plan`, and that name is what a user's guardrail rule points at, so it is never renamed. A plan is **one ordered list, and the list is the whole state**: every call replaces it, so there is no per-step update to reconcile and no store that could fall out of step with the session — the steps ride in the call's `details`, and the last plan row of the log *is* the plan a resumed session ended with. A step carries no owner and no delegation: it belongs to the session that wrote it. `lib/steps.ts` is the contract: it reads loosely (a bare string is a step not started, one value named in the list slot is a list of one, `doing`/`done`/`In-Progress` fold to the standing they mean) and refuses what it cannot mean — an entry with nothing to do, or a standing outside `pending`/`in_progress`/`completed` — taking the whole call with it and naming each step, because a plan that quietly lost its middle step is a different plan and the caller has no way to find out. `MAX_PLAN_ROWS` bounds what the row draws and what the answer reads back, never what the plan keeps, and the cut is counted. `lib/answer.ts` gives the model the plan read back — counts, then every step with its standing — which is the list it re-sends with one word changed rather than rebuilt from memory; `lib/toolView.ts` folds `details` into chips and rows, and `components/PlanToolRows.tsx` only chooses words: a step's number stands in the log's id column, its words in the body, its standing in the pill column the list shares, and the header says how far the plan has got and which step it is on.
- snapcompact compacts a context by photocopying it: the discarded span is serialized and printed — pixel font, black on white, ~14k characters per page — into dense PNGs a vision model reads back, instead of paying a model to reread it. **The engine is `@oh-my-pi/snapcompact`, and mu writes no rasterizer of its own**: the serializing, normalizing, shape table, rasterizer, PNG encoding and the summary's reading guide are that package's. mu owns three things around it — `lib/plan.ts` runs the pass inside pi's `session_before_compact` (an extension factory registered exactly as guardrails and codemode are, so pi still decides *when* to compact and where the cut is) and stores the frames in the compaction entry's `details` (pi never sends `details` to the model, which is what makes it the right home for pages); `lib/replay.ts` rebuilds them into the context on **every** request, because pi rebuilds the request from the session file and a guide pointing at pages that are not there is a lie — the blocks go into one `custom` message, the only pi role whose blocks mix text and images, standing in for the `compactionSummary` message; and `lib/reader.ts` is the one place mu's model record meets the other fork's (`provider`, `api`, `id`, `baseUrl`, `reasoning` and the image-input axis are all the package reads). The pass is local: no model call, no usage, nothing billed. mu declines it — and pi's summarizer answers — for a reader with no image input, for `/compact <instructions>` (an archive is not a *reading*), and for a span with no middle to page, where nothing was compressed; a session that moves to a text-only model after an archived pass still gets its history, as text, through the package's own `viewWithoutFrames`. The cost is `@oh-my-pi/pi-natives`: a 128 MB prebuilt addon (≈2 MB added to the compiled binary, plus one `.node` its loader finds in `dirname(process.execPath)` — `flake.nix` copies the baseline x64 build to `$out/lib/`), so `lib/load.ts` imports the package **on the first compaction that needs it**, never at startup. Arming is the user's file — `~/.config/mu/snapcompact.json` (`enabled`, `maxFrames`, `shape`; `MU_SNAPCOMPACT_CONFIG` moves the path), read at session start, unreadable means the defaults, and the agent cannot flip it. The session tree's compaction row and the transcript's compaction note read the frames back through `lib/note.ts` rather than the summary, whose first line is a reading guide.
- terminal is the third wide composer panel — the change stack (`ctrl+k`), the operation log (`ctrl+o`), the history tree (`ctrl+shift+t`) and the terminal (`ctrl+shift+enter`) — and it registers no agent tool, because a shell a person types into is not something the agent should be able to reach sideways. **It is a real pty, not a rendered picture of one**: `lib/pty.ts` is the only file in the app that names a C library call, and it takes `posix_openpt`/`grantpt`/`unlockpt`/`ptsname_r` plus one `ioctl(TIOCSWINSZ)` out of libc through `bun:ffi` (`src/bun-ffi.d.ts` declares that module, since bun ships no types for it). `openpty` is deliberately never called: it is the friendlier spelling and bun's FFI segfaults on it. The child is started under `setsid -c` where util-linux has it, so it becomes a session leader with the slave as its controlling terminal — without that a shell says "no job control in this shell" and Ctrl+C means nothing — and the parent's copy of the slave is closed right after the spawn so the read pump sees the end. `TERM`/`COLORTERM` are set by `openPty`, never inherited blindly.
- the VT half is **`@wterm/core`, wterm's headless core**: its Zig parser compiled to a ~50 KB WASM binary, addressed as cells. wterm's own renderer is DOM text (`@wterm/dom`, `@wterm/react`) and mu has no DOM, so nothing above the core is used and every terminal on screen is one mu paints — `lib/paint.ts` folds cells into runs (a cell per element would put thousands in a window that changes sixty times a second), `components/TerminalPanel.tsx` lays runs out in a flex row so columns agree by the font rather than by measured x, and the cursor is the cell under it inverted rather than a mark laid over the grid, which is the only way it cannot drift a column off its glyph. The core's WASM is embedded in the package as base64, so `bun build --compile` carries it: unlike photon and quickjs there is no asset to install beside the executable. Screen addressing is one line of retained history — `screen.cellAt(line, col)`, oldest line first — because the core stores the scrollback newest-first and the viewport oldest-first and that disagreement must not escape `lib/screen.ts`. A program's queries are answered from the same queue its bytes came off (`screen.answer()` drained into the pty), or vim sits waiting for a cursor-position report nobody sends.
- **the shell keeps the keys.** `isTerminalMode` (in `core/lib/composer/mode.ts`) plus `keyRouter.elementTakesKeys` shut the focused-element route for that panel entirely: a panel's keys reach the app twice, and an Escape taken by the element route would close the panel on the same keystroke that was handed to an editor as *leave insert mode*. The window route is the one that runs, its `wide.onKey` consumes everything `lib/keys.ts` can name, and only the chord that opened the panel gets away — so the hint line says the way out is that chord. `composer.terminalPaste` is `ctrl+shift+v` because `ctrl+V` is readline's *insert the next character literally*; scrolling the history is `shift+PageUp/Down` because plain Page Up belongs to the pager; `bracketedPaste` decides whether a paste is wrapped in `ESC [ 200 ~`. One shell per window lives in `lib/session.ts` under the hook, survives the panel closing (a build started there keeps building) and dies with the window; output is parsed as it lands and the repaint is coalesced to `REPAINT_GAP_MS`. The grid is counted, never measured at paint time: `lib/geometry.ts` turns the panel's room into cols/rows with one cell of slack across (the mono advance is the app's budget, not a measurement, and a column wider than the pane hides characters the shell believes it drew), and `session.resize` is what tells the pty — `stty size` inside the terminal answers with those numbers.
- Stories are the visual regression suite: `stories/` holds one scene per feature row of `README.md`, and `.storybook/fixtures` is shared between them. A story that imports a plugin file is a real consumer of it — check `stories/` and `.storybook/` before removing anything.
