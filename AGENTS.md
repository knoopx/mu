# mu — working notes

A GPU-rendered desktop client for the pi coding agent: `@gpuix/react` + `adwaita-gpuix`, no DOM, React 19, TypeScript strict, bun.

## Commands

- `bun run dev` — the app, hot (`bun --hot app.tsx`)
- `bun run typecheck` — `tsc --noEmit`; the tree is expected to stay clean
- `bun storybook .` — renders every scene in `README.md` to `stories/<Feature>/<story>.png`

## Layout

Each plugin is one folder under `src/plugins/`, and every plugin is built the same way inside: `lib/` for logic with no JSX, `components/` for what is drawn, `hooks/` for files whose export is a hook, `tools/` for the agent tools it registers, and `types.ts` and `constants.ts` at its root for what the whole plugin shares.

```
src/plugins/
├── core/            the app itself: registers no tool of its own, and adds screens/ for what fills the window
│   ├── lib/         agent/ codemode/ commands/ composer/ files/ project/ session/ theme/ ui/ utils/ workspace/
│   ├── components/  transcript rows, composer panels, project card, session tree
│   ├── hooks/       useChatSession, useSessionTree, useThemePanel, useWorkspaceStatus, ...
│   └── screens/     Chat.tsx
├── code-quality/    lib/ (cli/ fallow/ json/ review/ answer/ params/ toolView/) components/ tools/ types.ts constants.ts
├── interaction/     lib/ components/ hooks/ tools/askUser.ts types.ts constants.ts
├── guardrails/      lib/ (treeSitter/ rules/ rulesFile/ engine/ store/ panelRows/ coverage/ report/) components/ hooks/ tools/ README.md types.ts constants.ts
├── vcs/             lib/ components/ hooks/ tools/ types.ts constants.ts
├── web-search/      lib/duckduckgo/ components/ tools/webSearch.ts types.ts constants.ts
├── openui/          lib/ (programStore/ analysis/ answer/ params/ schema/ toolView/ format/ tokens/ theme/) components/ (library/) hooks/ tools/ README.md types.ts constants.ts
├── mermaid/         lib/ (diagram/ palette/ answer/ toolView/) components/ tools/mermaidRender.ts types.ts constants.ts
└── figures/         lib/ (plot/ answer/ toolView/) components/ChartToolRows.tsx tools/chartRender.ts types.ts constants.ts
```

A namespace is a folder inside a kind: the agent bridge is `core/lib/agent`, the composer's layout and mode logic is `core/lib/composer`, the DuckDuckGo engine is `web-search/lib/duckduckgo`, the OpenUI component library is `openui/components/library`. A tool is one file per tool, named after the tool: `interaction/tools/askUser.ts` is `ask-user`, `web-search/tools/webSearch.ts` is `search-duckduckgo`, `guardrails/tools/guardrailsTest.ts` is `guardrails-test`, `vcs/tools/vcsLog.ts` is `vcs-log` — the file is camelCase, the tool name it registers is kebab. A plugin that registers no agent tool has no `tools/`.

### Imports: no barrels

Nothing under `src/plugins/` re-exports a folder, and there is no `index.ts` in any plugin or namespace. Every import names the file it comes from: `../../core/lib/ui/theme`, `../../lib/composer/panelHeight`, `../../../interaction/tools/askUser`. Crossing into another plugin means naming that plugin's file — `core/lib/agent/agentService.ts` registers the ask tool by importing `../../../interaction/tools/askUser`, and `core/lib/project/projectSummary.ts` reads jj through `../../../vcs/lib/repo`.

Adding a file means adding its path at each consumer; there is no public surface to keep in sync, and moving a file updates only its own consumers.

### Naming

- a component file is PascalCase and matches the component it exports (`vcs/components/ChangesPanel.tsx` exports `ChangesPanel`). The one exception is a namespace of component *definitions* rather than components: `openui/components/library/layout.tsx` holds the `Stack`, `Row` and `Grid` definitions of one area of the language and `registry.ts` registers them — the area is the unit there, not one component
- a hook file is `useThing.ts` and lives in its plugin's `hooks/`, in the plugin that owns the thing (`useProjectSummary` in `core/hooks`, `useChangesPanel` in `vcs/hooks`)
- a namespace keeps its key hints in `shortcuts.ts`, and a plugin keeps what the whole plugin shares in `types.ts` and `constants.ts`
- when two modules in one namespace want the same name, the name is the thing that is wrong: the changes panel's state hook returns `ChangesPanelState` so the `ChangesPanel` component owns the name, and the composer counts rows in a height with `composerPanelRowsForHeight` so the panel's own `composerPanelRows` owns its name

## Stories

One feature, one story, one scene. Each story in `stories/` renders the app — the window, the log, the composer slot, the status bar — at the size the real window is used at, with a session in it doing the thing the feature is. A story is a picture of the app being used, not a component in a box. The PNG it writes is the image `README.md` shows for that feature, so the README stays a description of the app and every claim in it has a scene behind it.

- `bun storybook .` renders every scene to `stories/<Feature>/<story>.png`
- `bun storybook . --only Chat` renders one feature
- the capture keeps the declared window width and fits its height to what is painted, so heights are a starting point, not a promise
- fixtures live in `.storybook/fixtures` and are shared between features: transcript scenes in `scenes.ts`, tool rows in `tools.ts`, project history in `project.ts`, conversation trees in `tree.ts`, pasted images in `images.ts`
- the window-scale helpers live in `.storybook/chrome`: `chat()` puts a session in the window, `askInChat()` puts a question in the composer slot, `overChat()` opens an overlay over the log

A story id is the meta `title` over the exported scene, so `stories/Chat.stories.tsx` with `title: "Chat"` and `export const session` is the `Chat/session` scene, and it writes `stories/Chat/session.png`.

## Notes

- Path completion lives in `core/lib/composer/pathCompletion.ts`: the draft's trailing path token (`~`, `~/x`, `/x`, `./x`, `../x`, `@x`, anything with a `/`) is listed as a shell lists it, and the completion panel's query **is** the draft — `isCompletionMode` — so typing keeps editing the draft and Tab takes the highlighted path, a directory keeping the panel open. Tab is `editor.autocomplete`, handled in `composer/keyRouter.ts` with the `cycle` flag so the window listener never takes a completion twice. **A panel is a choice, never a send**: Enter takes the highlighted name in the completion panel exactly as in every other panel — `panelListKeys`'s `onEnter` is `pickActive`, and `ComposerField.onSubmit` picks whenever a panel is open — so path completion can never submit the draft to the conversation. With no name to take, Enter is inert; Escape closes the suggestions and leaves the characters typed, and Enter in the draft then sends them. `pathCompletionShortcuts` prints Tab's `complete` beside Enter's `use`.
- There is no DOM. Style objects are `StyleDesc` values and layout is flex; `adwaita-gpuix` owns theme tokens, and colour helpers live in `core/lib/ui/theme.ts` so a component never hand-mixes a hex.
- No component writes a bare number in a style. `core/lib/ui/tokens.ts` is the one answer to how big, how much space, what leading and what weight, and it defers to adwaita's scale where that scale already owns the value: `ROW_HEIGHT` is the height of every one-line row (the tree, a change feed, a picker), `monoColumn(t, chars)` *budgets* a column of monospace text and `monoTextWidth(t, chars)` measures what that text actually prints (`idColumn(t)` is the log's own column, budgeted), and `figureGap(t)` is the one role-gap the scale cannot name — the air between the figures a row trails, which five files used each to spell as `t.space.sm` on their own; `lineBox(t, role)`/`codeLineBox(t)` are the line boxes of text roles (`leadingOf` for a caller that sets a ratio), `emphasisWeight(t)`/`titleWeight(t)`/`plainWeight(t)` are the only weights, `MARKER_GLYPH`/`INLINE_GLYPH`/`STATE_GLYPH`/`ACTION_GLYPH` are the marks a row draws (`STATE_GLYPH` is the log's mark — a header glyph, a running spinner, a note's icon — and `MARK_HANG` how far it hangs into the page inset), `HAIRLINE` is every rule and edge, and `elevatedShadow()` in `theme.ts` is the one drop over the log, from `ELEVATION`. A plugin's own sizes stay named in its own file when nothing else asks for them (`MAX_ROWS`, `PANE_GROW`); what must not happen is two files spelling the same number differently. Secondary text is `mutedText(t)` — a call site never reads `t.color.text.dim`.
- The transcript page inset (`PAGE_INSET` in `core/lib/ui/transcriptLayout.ts`) is one constant imported everywhere; the adwaita tool-header glyph hangs 24px into it, so the inset stays at 56. The gutter of marks runs the whole height of the window: a running session is a `STATE_GLYPH` spinner hung the same `MARK_HANG` beside the composer box (`ChatComposerSlot`), not a line of prose at the end of the log. That mark is one component, `core/components/StateSpinner.tsx`, and it turns pi's own frames — the ten braille cells of pi's `Loader` (`DEFAULT_FRAMES`), one every 80ms (`DEFAULT_INTERVAL_MS`), in the accent tone — so a running session looks the same here as in the terminal; adwaita's ring `Spinner` is not used anywhere in mu, and the cell is set in the mono family because that is the family with braille coverage — there is no "Working" row and no loader in the transcript. The box keeps the exact x and width it had a moment before because the mark's row pays back the width the hang takes (`MARK_HANG - STATE_GLYPH` of margin), and the mark stands in that row rather than inside the composer's own root, whose fill clips its children.
- The log is a two-column grid and `core/lib/ui/toolRows.ts` owns it: **text** of every row — a header title, an answer's caption, a preview line, a system row — starts at `PAGE_INSET`, and every **mark** hangs `MARK_HANG` to its left, in `STATE_GLYPH`, because adwaita's `ToolHeader` puts its glyph there (`GUTTER_GLYPH`/`GUTTER_GLYPH_HANG`, neither exported) and nothing else in the log gets to pick a second column. So `toolColumn`/`toolGapColumn` open with `paddingLeft: 0` (a column that padded its own left edge indented every body line away from the head it answers), a row-leading icon takes `style={toolMark}` (`toolMarkIn(padding)` inside a column that really does pad), and a lone note is wrapped in `toolBodyStack` rather than returned bare. A plugin never hand-rolls an icon-plus-caption line: `ToolStateLine` (`ToolStateNote`/`ToolStatusNote`) and `ToolCaptionLine` are the only two, and they take `toolText(t)`, which puts a log line on `lineBox(t, "caption")` leading while `toolLine` keeps the row at least that tall — otherwise the rows of an answer sit tighter than the prose above them.
- Every panel in the composer slot — the draft's list panels, the question panel, the changes panel, the history panel — is framed by `core/lib/composer/chrome.ts`, and nothing else states their padding. `panelBox(t, tone)` is the band, and it pads itself by one unit — `panelPad` (`space.sm`) on **all four** sides, so `panelPageInset` and `panelPadY` are the same number and a panel breathes equally top, left, bottom and right. Everything the panel says then stands `panelInset` further in, so the ink column sits at twice the band's breathing from the left and right and one measure from the top and bottom — a 1x2 width-to-height ratio, an equal band being its degenerate case, and the reason a second padding number in a panel is a bug rather than a taste (a chip or an inline mark is not a band and keeps its own measure). The field, the list, the hints line and the notes all stand in that one column, and a row's hover band simply runs `panelInset` wider than its text. `panelChrome(t)` owns the panes (`listPane`, `flexPane`, `widePane`, `previewPane`, `previewCode`), the rules (`ruleV`/`ruleH` take the colour a panel's tone asks for, since tone is the one thing chrome cannot know), the `rowSlot` a virtual list stands one row in, and the `emptyPane`; `ChangesPanel`, `SessionTreePanel` and `AskComposer` all read it rather than restating it. `panelHeight.ts` does the arithmetic over those same numbers — `panelChromeHeight(t, slots)` charges a panel only for the slots it draws, and the wide panels draw no draft field — so a padding moved in `chrome.ts` moves a row budget with it. `lib/composer/field.ts` is the one answer for the draft every panel types into: `panelInset` of left padding and `fieldPadY` of breathing (floored, so a one-row field plus its pad stays inside `ROW_HEIGHT`), whether it holds one line (`composerFieldLineStyle`) or grows with its text (`composerFieldBox`). `paneInk(t)` is the padding of the ink a pane holds that is *not* a row — the preview pane (`previewPane` pads itself with it, so adwaita's `DiffPanel`, mu's `previewCode`, an image tile's caption and a pane note all land under the file paths above them), the question panel's title, context, detail and hint row. `panelGap` is the air between one panel's slots and `paneGap`/`ruleGap` are exactly twice it, so nothing writes `t.space.md` between two panes.
- The figures the status bar keeps in view are the **session's own, read live**. `core/lib/agent/turnStats.ts` is the only place they are computed: one `scan` over the log's rows answers what the provider has reported, what is still streaming, and when the rows last did something, and `conversationStats(items, clock, sessionStart?)` folds that into the bar's turns, tokens, span and rate — a span from the log's first timestamped row to its last activity, never from when the window opened, so a resumed session says its own length and a new one starts at zero. `useRunningClock(running)` (`core/hooks/`) ticks `now` while a run is in flight and `Chat.tsx` hands it to `useTranscriptView` as a `SessionClock`, so elapsed time keeps moving through the seconds a turn spends in its tools, where nothing streams. A decode in flight has no usage to read — a provider answers at the end of a message — so its tokens are *estimated* at four characters each, the estimate pi's own compaction makes, and the row carries the timing for it: an assistant row keeps `startTs` from `message_start` and a tool row `endTs` from its result, so the live figure counts streamed prose, reasoning, and the arguments of the calls the streaming message is still writing, and never the arguments of a call that already ran (its tokens landed in a usage figure). `ConversationStats.live` says the rate is being measured now, and the bolt segment stands in the accent while it is. Turn footers stay settled-only: `turnStatsById` answers a turn's figures with no estimate, because the moving numbers belong to the bar. `ChatAppProps.now` pins the clock for a story — `.storybook/fixtures/turn.ts`'s `clockOf(items)` puts a scene's moment a moment and a half past its last row — so a scene with a running turn captures the same PNG twice.
- Images go through pi's own pipeline and `core/lib/agent/settings.ts` overrides nothing in the `SettingsManager` it builds for `createAgentSessionServices`: an image is converted to a supported format, EXIF-corrected and downscaled under the provider's inline limit, and the note pi adds tells the model the coordinate scale. Every resize path reads `photon_rs_bg.wasm` **from disk** — the resize worker cannot start from an embedded bundle, and photon's glue asks for the build machine's path — so a `bun build --compile` binary resizes only if the package installs that wasm where pi's loader already looks, beside the executable (`flake.nix` puts it in `$out/lib/`). Without it `resizeImage` returns null and every image answers "[Image omitted: could not be resized below the inline image size limit]", at any size. There is no `images.autoResize` override: an in-memory `applyOverrides` is wiped by pi's `SettingsManager.reload()` during resource loading, so it was inert anyway.
- Anything an embedded dependency reads with `fs` at runtime, rather than through an `import`, has to ship as a file: `photon_rs_bg.wasm` beside `$out/lib/mu`, and QuickJS's `quickjs.wasm` under `$out/lib/node_modules/quickjs-wasi/` with the wrapper setting `NODE_PATH` there, because inside a compiled binary `require.resolve` searches `NODE_PATH` and the process cwd and never the executable's directory. Guardrails' grammars are the opposite case — `with { type: "file" }` imports, so `bun build --compile` embeds them.
- codemode's worker is a compile entrypoint, not just a module: in a bun-compiled binary pi spawns it at the literal path `./src/extensions/codemode/worker.ts`, so mu keeps that one-line shim at exactly that path (the path is pi's, and moving it breaks codemode) and `flake.nix` passes it as a second entrypoint to `bun build --compile`. That is why `@earendil-works/pi-codemode` is a direct dependency.
- Guardrails are driven by three agent tools in `guardrails/tools/`, named after the pi tools they port: `guardrails-test` runs a fixture suite against the live engine, `guardrails-fixture-update` writes the suites, `guardrails-coverage` reads saved session transcripts for observed blocks. There is no manage tool: arming is the panel's — `guardrailsStore` switches, driven by `/guardrails` and the composer keybinding, and the agent never arms, disarms, clears the log or dry-runs. **Guardrails are the user's files, never the project's and never pi's**: rules are `$XDG_CONFIG_HOME/mu/guardrails/<domain>.json`, the suite that proves a domain sits beside it as `<domain>.fixtures.json`, and the arming the app remembers is `$XDG_STATE_HOME/mu/guardrails.json`. `lib/rulesFile.ts` is the one that knows those paths (`rulesDir`/`fixturesDir`/`stateFilePath`, with `MU_GUARDRAILS_RULES` and `MU_GUARDRAILS_FIXTURES` as overrides, `saveGuardrailRule`/`deleteGuardrailRule` as the writers); `startGuardrails()` reads the rule files into the registry at boot and `reloadGuardrails()` reads them again. A domain is the filename, so a rule and its file can never disagree, and one unreadable file loses only its own rules. The format, the validation each record passes, and why a rule needs a `block-*` and an `ok-*` case are in `guardrails/README.md`. mu writes no rules: `lib/rules.ts` is the registry and the validator, and no tool authors a rule.
- A guarded call is a list of **sources**, and a source is one key's text in one grammar: the `command`/`cmd` of a command tool is bash, and the `content`/`newText`/`oldText`/`text` a file tool writes is parsed in the grammar its `path` names, so an `edit` of a `.py` file is checked against python rules and a `write` of a `.json` file is released unread. Those key tables are `core/lib/agent/toolInput.ts`, which guardrails imports rather than spelling again: the log reads the same keys to say what a call was pointed at. All sixteen grammars `@vscode/tree-sitter-wasm` ships are registered — bash, cpp, csharp, css, go, ini, java, javascript, php, powershell, python, regex, ruby, rust, tsx, typescript — imported by name in `treeSitter/grammar.ts` so `bun build --compile` embeds them, and booted only for the languages the registry names. A rule that reads file text says so with `tools` and `fields`; a rule naming neither reads command text only, which is what every rule written before file sources did. The format, the source table and the fixture shape are in `guardrails/README.md`.
- Guardrails parse in-process with web-tree-sitter, on the app's JS thread. A rule is a tree-sitter query plus JS regex filters: a `#match?` written on a bare `(program) @root` has its predicate ignored by the query engine, so whole-command tests live in `filters` where they are checked. Grammars come from `@vscode/tree-sitter-wasm` — a `dylink.0` custom section is required, and the prebuilt `tree-sitter-wasms` set is refused by every web-tree-sitter since 0.20. `Parser.init()` must be handed `wasmBinary` bytes read from an embedded `with { type: "file" }` asset, because its own resolver finds no `.wasm` inside a `bun build --compile` binary, and Bun cannot start an embedded worker there, so a parse is budgeted (`PARSE_BUDGET_MS`) and always fail-open.
- vcs is two composer panels — the change stack (`ctrl+k`) and the operation log (`ctrl+o`) — and ten agent tools in `vcs/tools/`: `vcs-log`, `vcs-file-diff`, `vcs-file-history`, `vcs-file-history-show`, `vcs-conflicts`, `vcs-oplog` and `vcs-hunk-list` read, and `vcs-describe`, `vcs-file-split` and `vcs-hunk-split` write. Those ten names are what the user's guardrail rules point an agent at, so they are never renamed or aliased. `lib/ops.ts` is the only file that names the change-tracking CLI: a tool names a revision, files, hunks and a message and never a flag, and answers in one status vocabulary (`ok`, `failed`, `unsupported`, `empty-selected`, `empty`, `none`, `binary`) rather than an exit code, and a write is verified by re-resolving the post-state so a tool reports the ids the repo resolved and never the ones the caller typed. A result is written for two readers: aligned-column text in `content` for the model and structured `details` for the GUI, both built in `core/lib/agent/toolText.ts` and folded by `lib/toolView.ts`, painted by `vcs/components/VcsToolRows.tsx`, dispatched from `core/components/ToolExecution.tsx`. `lib/answer.ts` is the only place a failure is answered: `noRepoResult`, `failedResult`, `missingResult` and `unresolvedResult` take the tool's `VcsBlank` — its scope fields with nothing resolved in them — and fill the status fields and the CLI the answer came from, so a details shape cannot be half-updated in one branch; `lib/splitOutcome.ts` runs the guard both splits share, and `lib/params.ts` states the bounded reads' `limit`/`offset`/`oldest_first`/`format` and a write's non-empty text once, the way code-quality states `limit` once for its six tools. The panel's describe (`d`), split (`s`) and split-hunk (`h`) keys send an instruction built in `lib/instructions.ts` — `ChangesPanelOptions.onInstruction` → `composerActions.sendInstruction` → `chat.send` — rather than typing a message or running the write locally, so no describe or split happens without a tool row behind it. Squash, revert, drop, bookmark and push are the panel's own writes and run in `lib/repo.ts`, which is what the panels read through; `lib/ops.ts` is what the tools read through. The preview pane picks by file, not by patch text: `lib/preview.ts` chooses between adwaita's `DiffPanel` (its diff rows, or its `DataTable` when a csv/tsv/tab file parses as two tables) and the two pictures of an image file, whose bytes `loadFileBytes` in `lib/repo.ts` reads binary-safe out of `jj file show` at the change and at its first parent — `run()` decodes stdout as text, so a patch cannot carry a picture.
- The op log panel is the same panel shape one level deeper: `hooks/useOplogPanel.ts` wires `hooks/useOplogData.ts` (rows, cursor, patch) to the keys, and `components/OplogPanel.tsx` draws it. One `jj operation diff --op … --git` answers a whole operation, so `lib/opPatch.ts` cuts that patch into file rows and per-file blocks instead of one call per file the way a change's files are read, and an operation's patch is immutable, so it is cached (`OP_PATCH_CACHE`). Its restore (`r`), undo (`u`) and redo (`U`) are the panel's own writes, in `lib/repo.ts` beside squash and drop: jj's answer to a mistake is an operation, no agent tool names one, and the panel re-reads everything after them because an operation moves the whole workspace. The two panels share what they genuinely share — `components/PanelList.tsx` for a virtual list, `components/FilePane.tsx` and `components/FilePreviewPane.tsx` for the whole right half, `components/PaneCaption.tsx`/`PaneEmpty.tsx` for a pane's own words, `lib/rowText.ts` for how a row is worded, `hooks/usePanelListRefs.ts`, `hooks/usePanelNav.ts` and `hooks/useRepoWrites.ts` for the lists, the cursor and a write, and one `widePanelSpec` in `core/components/composer/panels.tsx` that serves `changes`, `oplog` and `tree` by target.
- A diff is drawn from **rows, not from the patch text**. `adwaita-gpuix/src/lib/vcs/rows.ts` is the one parser: `diffRowsOf(patch)` answers `DiffRow[]` (a file row, a `@@` row, and one row per line — `add`/`del`/`ctx`), each carrying a stable `id` (`f0h1+42`) so an answer about its text can be handed back to it, and `diffRowsShown` answers what a pane shows and how many rows a cap cut off. `components/vcs/DiffText.tsx` paints those rows: an added or deleted line is a tinted row of text and that is the whole of it — **no line-number columns and no `+`/`-` marker in front of the text**, because the row's colour is what says what happened to it. `DiffPanel` is a pane's diff (`scroll`: the rows stand in a virtual list, and the pane's `diffRef`/`makeDiffScroller` moves them) and `ToolDiff` is the log's (no scroller of its own, capped by `maxRows`, the count it left out said in one caption). **What the text is made of is the app's business, not the widget's**: `core/lib/syntax/` reads the rows with the tree-sitter runtime guardrails already boots — `loadGrammar` and `parseWithinBudget` from `guardrails/lib/treeSitter/runtime.ts`, `languageOfPath` from its `source.ts` — classifying a node by its **name** (`comment`, `string_content`, `type_identifier`, `property_identifier`) plus one keyword word-set, all in `kinds.ts`, and answering `DiffToken[]` per row keyed by row id. Each hunk is read **twice and with its undrawn context lines** — the file as it was from `ctx`+`del`, as it is now from `ctx`+`add` — because that context is what makes a line in the middle of a function parse as part of one; a missing grammar, a blown time budget or a language with no grammar answers with nothing and the row is drawn in one colour. `core/hooks/useDiffTokens.ts` is the async half (rows drawn plain, then painted when the read answers) and `core/components/PatchDiff.tsx` is the log's one entry; the colours themselves are `codePalette(t)` in adwaita's `theme/code.ts`, since the library owns the palette and the app owns the parse.
- A tool row's trailing **figures stand in columns the list reserves**, not at whatever x its own words leave: `figureColumnsOf(rows, t)` in `core/lib/ui/toolRowPaint.ts` measures the widest badge, trailing figure and meter across the rows, and every row then stands a slot in each column it has (`toolFigureRow` groups the slots with `figureGap`, `toolFigureSlot(width)` is one column). A list is a `ToolRowList`, and a `ToolSections` measures across **all** its sections, so the meter under a `high` is not shoved sideways by a `moderate` in the row below it. The slot widths are budgets from `tokens.ts` (`textWidth`/`badgeWidth`, one proportional advance like `MONO_ADVANCE`), and the meter's track paints in `divider.default` because an invisible track leaves a score reading as a dash of no particular length.
- **A rule is painted with `t.color.divider.default`, never `divider.faint`**: in nightsky `faint` is the log's own background and in dark it is the card's, so a faint row rule, cell rule, meter track or program rule draws *nothing* — the table is left without the lines that make it a table. `divider.faint` is only ever an edge on a surface that fills itself (a chip over its `surface.button`), and that is the whole difference. openui says the same thing once: `programRule(t)` in `openui/lib/theme.ts` is every rule a program draws, and the program tone `"faint"` is faded *ink* (`withAlpha(text.secondary, .6)`), never that hairline colour — a tone that paints the card's colour is invisible text. A program row rule that reached for a divider colour by hand is how `data.tsx` ended up with one rule in `default` and the next in `faint`.
- A tool result is painted by one set of primitives in `core`, because two plugins drawing their own rows is where the copies started. `core/lib/agent/toolText.ts` is how an answer reads (`toolResult`, `blocks`, `tableOf`, `statusTable`, `missing`, `counted`, `clipText` at `TOOL_PREVIEW_MAX`); the first non-empty line of any blob is `firstLine` in `src/utils/truncate.ts` — one implementation, because four files had written the same five lines and they had already begun to differ; `core/lib/agent/toolPreview.ts` is the single line a tool header shows, driven by a `ToolPreviewVocabulary` the plugin supplies; `core/lib/ui/toolRowPaint.ts` holds the tone/badge/status vocabulary and the row styles, including `ToolPaintRow` and the `ToolPaintSection` group of rows; and `core/components/ToolDataRows.tsx` draws `ToolChips`, `ToolRowList`, `ToolSections`, `ToolStatusNote`, `ToolTruncated`, `ToolSummary`, `ToolStateNote`, `ToolUnknownResult` and `ToolRunning`. `ToolDataRow` and `ToolSectionHead` are private to that file: a plugin reaches a row only through the list or the section, so it cannot paint one of its own. A plugin's `lib/toolView.ts` folds its `details` into `ToolPaintRow`s and its `components/*ToolRows.tsx` only chooses words, badge variants and its own status tones — the note of a view and its omitted count come from `ToolStatusNote` and `ToolTruncated`, which read the shared status vocabulary. `core/lib/ui/toolOutputMode.ts` decides code-vs-markdown from a call's **shape** — `commandTextOf` reads `command`/`cmd` in its args, from the key tables in `core/lib/agent/toolInput.ts` that guardrails reads too — and never from a list of tool names: mu's tool set is fixed by `APP_TOOL_NAMES` in `core/lib/agent/agentService.ts` with `noExtensions` and MCP off, so `bash` was the only live entry in the old `PLAIN_OUTPUT_TOOLS` and `shell`/`terminal`/`exec`/`run`/`powershell`/`ls`/`grep`/`find` were names no call ever had. Guardrails keeps its name lists (`GUARDED_COMMAND_TOOLS`, `GUARDED_FILE_TOOLS`) on purpose: a rule is the user's and must be able to name a tool the app has never seen. **A command's own colours are the box's business, not mu's**: `OutputBox` in adwaita reads the SGR text a command printed (colour, weight, dim, underline) and draws the rest of the grammar — cursor moves, erases, titles, background fills — as nothing, so mu strips nothing on the way to it and `src/utils/strip.ts` stays a width-measuring helper. pi's bash tool keeps those escapes in the result it hands mu (only pi's own TUI calls `stripAnsi`, and its HTML export converts them with `ansi-to-html`); a command emits them when it is told to (`grep --color=always` wraps each run in an SGR pair and an erase-between-columns), which is why a plain `ls` row stays plain.
- codemode is pi's own tool, so `core` draws its row: `core/lib/codemode/` (`script.ts` for the call, `answer.ts`/`calls.ts`/`toolView.ts` for the answer) and `core/components/CodemodeToolRows.tsx`. A script's output is text it printed, never prose it wrote, so it goes to the output box (`plainOutputOf(body, MAX_OUTPUT_LINES, "head")` — a script answers with its point first, so the budget keeps the head) and never through `Markdown`, which folded pi's `==> text 1/5 <==` separators and `<console_output>` block into one paragraph. `codemodeAnswerOf` strips pi's `Script completed` / `Wall time …` / `Output:` header and the wall time comes back as a `Took 4.2s` caption, exactly as pi's own renderer does. A script's own tool calls never reach the model: `eventHandlers` drops a `tool_execution_*` event that carries `parentToolCallId` (a nested call is not a transcript row), and the row lists them from `details.calls` — one `ToolPaintRow` each, numbered, badge only when the call is running, cancelled or failed — which is also where a guardrails block of a nested call surfaces, as that row's error line. `tool_update` carries `details` too, because a script publishes its calls as it makes them and answers with output only when it ends.
- code-quality registers six tools (`code-complexity`, `code-dead-code`, `code-duplicates`, `code-review`, `code-symbol-inspect`, `code-symbol-references`) and drives two external analysers through `lib/cli.ts`, the only file that names a binary: `fallow` for complexity, unused code, clones, a file's surface and a symbol's call chain, and `inspect` for entity-level change review. **The analyser is not the agent's concern, so nothing the agent reads names it**: no `description`, `promptSnippet`, `promptGuidelines`, parameter description or answer text mentions `fallow`, `inspect` or `bunx`, and an unavailable analyser is reported as "the project analyser is not installed or not on PATH", never as a binary name. The name survives only in `constants.ts`/`lib/cli.ts` and in `details.analyzer`, which is app-side and paints the log chip for the human. A tool names a subcommand, its scope and a limit, never a flag; `lib/fallow.ts` reads the JSON envelope into the details types, `lib/answer.ts` is the head and the nothing-found branch every tool shares, and `lib/params.ts` states `limit` once for all six.
- openui answers with a screen: the language is `@openuidev/lang-core` (parser, evaluator, action plan, prompt generator) and mu owns three things around it — the **component library**, the **renderer** and the **store**. The unit is the **program, not the tool call**: `lib/programStore/store.ts` holds each named program (source, parse, the `$variable` values as the human left them, the interactions waiting, and what the last paint published back), and the **anchor** is the tool row that paints it — a render or stream that creates a program takes the anchor, a later call that edits it keeps it, so one screen is painted once in the log and stays live. One program is **showing** (`liveName`), which is what `openui-state`/`openui-events`/`openui-switch` read when named; programs are in memory only, so a resumed session keeps its rows and its row says `no longer in the log` rather than inventing a screen. The eleven tools (`openui-prompt`, `-library`, `-validate`, `-render`, `-stream`, `-state`, `-events`, `-tools`, `-list`, `-switch`, `-clear`) are what a guardrail rule and a story point at, so they are never renamed. `lib/programStore/verbs.ts` is the only writer of a program and `lib/analysis/parse.ts` the only parser (one parser built from this app's library schema, so a component name is the same answer in `openui-validate`, in a row's error count and on screen). `lib/answer.ts` is the whole answer a write gives — `programWriteAnswer` holds the refusal, the head columns, the store's status line and the diagnostics, so `openui-render` and `openui-stream` say it alike and only choose their words (`refusal`, the extra `columns`, whether a half-written program's warnings count, the hint); `lib/format.ts` words those columns and `constants.ts` names the default program once.
- **The registry is the language's whole boundary**: `components/library/{screen,layout,text,data,figures,lists,inputs}.tsx` carry both halves of each definition — `defineComponent({name, props, description, component})` for the parser and the prompt, and the drawer `drawThing(node, ctx)` for the screen — and `registry.ts` lists them in the seven groups (`Screen`, `Layout`, `Text`, `Data`, `Figures`, `Status`, `Inputs`) with `notes: []` on every one — the doctrine those notes used to carry was invented in that file, enforced nowhere, and read back as if the library guaranteed it; a fact a drawer really implements goes in that component's own `description` instead. `openui-prompt` also empties the notes on the way in (`referenceSpec()` in `lib/analysis/prompt.ts`), so the reference carries signatures and nothing else — no rules of mu's, no example programs, and no `additionalRules`; a component absent there does not exist and the parse drops it as `unknown-component`. `figures.tsx` (Tree, Timeline, Trace, Heatmap, Breakdown) and `lists.tsx` (Sections, Todos, Steps) draw a shape rather than cells, and each is an adwaita widget — `FileTree` with `variant: "list"` and its `+N -M` columns measured across the whole tree, `Timeline`, `Trace`, `ContributionHeatmap`, `SegmentBar`, `ProgressBar` — so a program's figure wears the colours, ramps and mono columns the app's own panels wear. `components/library/rows.ts` is the only reader of a row: a row is a list of cells or an object of named fields, `cellOf(row, names, at)` answers both, `statusOf` folds the state words a program writes loosely ("complete", "wip", "cancelled") into `ProgramStatus`, and `isFigure` is what makes a numeric cell mono and right-aligned. A block states its count in `Pane`'s `trailing` rather than in a caption above it, and a `tone` on a `Pane` puts the mark before the title the way a tool header does — both drawn from the one status/tone vocabulary in `lib/theme.ts`. `lib/schema/library.ts` turns that one list into the JSON Schema the parser is built from, the spec `openui-prompt` generates from, and the index `openui-library` prints. A drawer never touches the store: it reads theme, children, a reactive prop and an action through `ProgramContext` (`components/library/context.tsx`), where `binding()` is the one answer for a prop marked `markReactive` (it reads `isReactiveAssign(...).target` and writes through the store, which is what makes a picked filter change a table without another message) and `listProp`/`listOf`/`textProp` are the only reads of a prop's **shape**: one value named in a list slot is one item — `Pane(title, blocks, surface, tone, Caption("biggest 412"))` puts a bare element where the schema says an array and the parser says nothing, and a drawer that reached for `.map` on it killed every block of the program — and a text slot prints text or nothing, since React refuses an object as a child and the screen goes with it; a drawer never writes a bare number either — `lib/tokens.ts` says what a program's `gap 3` and `Title(_, "lg")` count for and `lib/theme.ts` what its colour words mean. `lib/analysis/run.ts` holds one runtime per program outside React — the query manager's cache has to outlive the row — and a late answer repaints the screen only while three things agree: `programStore.touch()` notifies on the next microtask, because a query answers when it likes, including inside the paint that asked for it, and React refuses a re-render asked for during a render; the runtime counts its answers and `useProgramPaint` puts that count in the paint's key, since a key the answer cannot move is a memo that answers the same way; and the runtime remembers what it was last **asked**, so a repaint that reads the same queries does not ask again — a query that failed has no cached answer, so asking again would fail again for as long as the screen is drawn. A `$rows = Query(...)` answer reaches the tree through `getState` reading the query snapshot over the declared values (`resolveRef` is only for a `RuntimeRef`, so a read that knows only the declared values draws every query-backed list empty). It evaluates the tree, and runs the local half of an action plan: `@Set`/`@Reset` change the page, `@ToAssistant`/`@OpenUrl`/custom actions are queued for the agent. A `Query(name)` has no backend but the JSON `openui-tools` served, and an unserved name **fails open** — the failure is published to the program and `openui-state` prints it rather than showing an empty table.
- figures is one tool, `chart-render`, and that name is what a user's guardrail rule points at, so it is never renamed. `lib/plot.ts` is the **one plot contract**: it reads the points a tool call sends as typed JSON *and* the points a program's `Chart` writes as source text, and it owns the series names, the point cap and the measure (axis span, range, total, mean, peak). A tone stays a word and the series ramp is resolved **at paint time**, so a plot travels in `details` as data and never as a bitmap — which is why re-theming redraws a chart and a resumed session still draws one, unlike an openui program. `openui/components/library/data.tsx` reads that file instead of keeping its own coercion (its `CHART_*` geometry moved to `figures/constants.ts`), so a program's plot and a tool's plot cannot drift; the one thing that differs is what a caller does with a value that is not a number, because only one of them can answer back: the tool refuses the whole call and names the point the cell sat on, a drawer draws what it could read. The model never sees the plot: `lib/answer.ts` gives it a reading — points plotted, the axis, range, total, mean, peak, and the points as figures, `…N not shown` past the readout budget and `…N not plotted` past `MAX_POINTS`, which is the sign to group the values. `components/ChartToolRows.tsx` paints `AdwaitaChart` and the `ChartLegend` a multi-series plot needs — adwaita exported the legend and nothing drew it, so a program's series were unnamed colours named `s1`.
- mermaid is one tool, `mermaid-render`, and that name is what a user's guardrail rule points at, so it is never renamed. `lib/diagram.ts` is the only file that names the engine (Pele, pure JS: it measures text from its own metrics, so it needs no DOM and ships no runtime asset); it answers in one status vocabulary — `ok`, `failed`, `empty` — and a parse failure arrives as `code`/`line`/`column`/`snippet`, never as a thrown parser error. `lib/palette.ts` is the only place a diagram's colours are decided: Pele emits `var(--pele-*)` roles and leaves every `<text>` element unstyled (it expects a stylesheet it never ships), so the roles are resolved against the app's theme and each text node is told its font, size and fill **at paint time**, in the row — which is why the raw SVG markup travels in `details` and `components/MermaidToolRows.tsx` draws the picture rather than the tool. The model never sees the picture: `lib/answer.ts` gives it a reading instead — the kind, the canvas, and every label the diagram says — and a missing label is how a wrong source is caught. There is deliberately no rasteriser: `@resvg/resvg-js` is a NAPI binary whose loader would read the `NAPI_RS_NATIVE_LIBRARY_PATH` mu sets for `@gpuix/native`, and the picture is a vector the log scales into `DIAGRAM_BOX_*` anyway. `path` writes the `.svg` (full size, no scaling) so a diagram can be committed.
- Stories are the visual regression suite: `stories/` holds one scene per feature row of `README.md`, and `.storybook/fixtures` is shared between them. A story that imports a plugin file is a real consumer of it — check `stories/` and `.storybook/` before removing anything.
