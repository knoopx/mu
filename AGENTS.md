# mu — working notes

A GPU-rendered desktop client for the pi coding agent: `@gpuix/react` + `adwaita-gpuix`, no DOM, React 19, TypeScript strict, bun.

## Commands

- `bun run dev` — the app, hot (`bun --hot app.tsx`)
- `bun run typecheck` — `tsc --noEmit`; the tree is expected to stay clean
- `bun run test` — `bun test`; a plugin's logic tests sit beside the file they grade (`lib/read.test.ts`), and they take the seam, not the network: a page read is graded with its loader handed in. The suites in `test/` paint the app in a headless gpuix window and assert what the screen actually shows — see **Tests** below

## Layout

Each plugin is one folder under `src/plugins/`, and every plugin is built the same way inside: `lib/` for logic with no JSX, `components/` for what is drawn, `hooks/` for files whose export is a hook, `tools/` for the agent tools it registers, and `types.ts` and `constants.ts` at its root for what the whole plugin shares.

Every plugin folder carries `plugin.tsx` at its root as well: the setup the host runs, which is the whole of what the plugin gives the app. It is not PascalCase because it registers rather than draws — the same reason `openui/components/library/layout.tsx` is not.

Every plugin folder carries a `README.md` too, in one shape: a title line, a short pitch, `## What you get`, then how it works and what its bounds are. The three long docs (guardrails, openui, snapcompact) keep their own sections after `What you get`, which is the part a reader wants first. This is the only place a reader finds out what a plugin is for: the README at the repo root is a gallery of screens and the keymap lives in these notes, so a plugin with no page is a plugin nobody can discover.

### A plugin registers into the host; the app draws from the host

`src/plugins/<name>/plugin.tsx` calls `definePlugin(name, identity, (app) => …)` and registers into the API the host hands it, and nothing else: `app.tools.register`, `app.extensions.register`, `app.log.rows`, `app.log.block`, `app.composer.panel`, `app.composer.command`.

The identity is four fields the plugin says about itself — `title`, `summary` (one line), `icon`, `category` from the small vocabulary in `manifest.ts` (`core`, `agent`, `project`, `surface`, `safety`, `session`) — and `definePlugin` refuses one that cannot state them. It exists because the app has to be able to talk about what it is made of: the plugins panel (`/plugins`, `ctrl+shift+a`) lists every plugin with the counts the host watched it register, and a refusal can name a plugin in prose rather than only a folder. The counts are never typed in by hand, so the panel cannot drift from the app.

**A plugin can be switched off, and only the user does it** — `core/lib/plugin/store.ts` keeps `$XDG_STATE_HOME/mu/plugins.json` (`{ "disabled": ["<name>"] }`) and the panel flips it; the agent has no tool that arms or disarms, exactly as with guardrails. `registry.ts` reads the file before `createPluginHost`, which skips a disarmed plugin's setup so it takes no tool, no panel, no keybinding and no command, and keeps it in `host.disarmed` so its row still shows, with `off` where its figures were. `core` is the one plugin the store refuses to switch off — it is the window itself, and turning it off would leave no way to pick a model. The switch belongs to the next start and the panel says so in its status line: the host's slots _are_ the app's shape, and a shape taken away mid-session leaves the system prompt, the open panels and the keymap remembering three different apps.

The shape these notes describe is held by what each checker can actually see: the host refuses a registration that breaks the app, the typechecker refuses an import that names a file which is not there, and the rest — every plugin folder has a `plugin.tsx` and is in the registry list, no `index.ts` and no `export * from` anywhere in the tree, every folder has its `README.md`, every plugin-to-plugin import names the file it comes from — are conventions a reader enforces when reviewing: an edge has to be typed out twice to exist, which is the point of naming the file. `core/lib/plugin/manifest.ts` is what a plugin and its surfaces _are_ (the types); `core/lib/plugin/host.ts` is the API and the slots the registrations land in; `core/lib/plugin/surfaces.ts` is the only reader of those slots. There is no table of plugin data core reads and no plugin module core reaches into — the dependency points one way, and a plugin cannot reach the app by any other door, because the API is the only way in.

`src/plugins/registry.ts` runs the fifteen setups in the order their tools reach the model and exports the one `HOST`; that list is the app's shape in one place. The host checks as it registers, and stops the boot: one tool name to one owner, one target and one chord to one panel, a tool that names no mark for its log row (`icon` on the tool it registers, held in `slots.toolIcons`), a row surface that owns calls and draws nothing, a wide panel with nothing to draw, a plugin that registers nothing at all — a tool the model silently never had is not a bug a user can report. **Read `HOST` inside a function, never at module scope**: the host is still being built while a plugin's modules are being pulled in (the panel data names the session, the session names the agent bridge), so `appToolNames()`, `isolatedResourceLoaderOptions()`, `composerHotkeys()` and `slashCommands()` are functions, and a `const` that read a slot at import time throws on boot.

**Core registers its own surfaces through the same API** — `core/plugin.tsx` registers the codemode rows, the ten composer panels and the nine slash commands the window owns (the last pair being the plugins panel and `/plugins`, which list what the build is made of). That is what keeps the API from growing a plugin-only side door, and it is why no core file names a plugin: adding a tool is one file in `tools/` and one line in that plugin's own `plugin.tsx`, and the forty imports and eight name splices that used to sit in `agentService.ts` are gone.

**A panel is one surface that owns its own state.** A `PanelSurface<State>` names its target, its chord, the event that opens it and the words it prints beside its keys (`choose`/`deletes`/`opens`/`edits` — a word a panel does not name is a key it does not take); it builds its own state in `use(ctx)` — the plugin's own hook, handed `PanelContext`: `cwd`, `toast`, `query`, `open`, the window size and `actions` (`pickText`, `sendInstruction`) — and `panel(state, data)` returns the `PanelView`: `rows` for the list core frames, or `node` for a panel that fills the band, plus its status line, its keys, and what it says while it reads or when it has nothing to show. `State` is the plugin's own type: `core/lib/composer/panelData.ts` holds it in `panelState`, a map keyed by target, and names no plugin's shape; `useChatPanels` runs the surfaces' `use` in host order (the panel list is fixed once the plugins load, so the hooks are the same hooks every render) and hands the map back to whoever made it. A panel whose rows mean something of their own answers its own pick — `pick(row, state, actions)` is how arming a guardrail stays a switch rather than a case in core's list routing — and a panel that puts a dialog over the window, not in its band, says so with `overlay(state)`; core draws what answers and opens no panel's dialog of its own. `core/components/composer/panels.tsx` is chrome only — the band, the list, the preview pane, the height math — and names no plugin and switches on no target, so a plugin that takes a panel takes it whole: the change stack's component, status wording and keys are `vcs/plugin.tsx` and `vcs/lib/panelStatus.ts`, the terminal's are `terminal/plugin.tsx`, the guardrails list's are `guardrails/plugin.tsx`, and the conversation tree's are core's own. The view is asked **once per composer render** (a `WeakMap` keyed on the data bag): the rows are measured for the cursor before the band is laid out, and a panel whose rows are a filesystem walk would otherwise walk the project twice a render. A `CommandSurface` carries the panel it opens, so `/changes`, `/oplog`, `/terminal`, `/guardrails` and `/tree` are registered by the plugin that owns the panel; only `/compact` and `/new` act on the session, and they are core's.

**The frame is core's, never the plugin's**: a surface supplies a `body` and the log draws the band over it, with `frame: "page"` the one exception a plugin may ask for — a program screen brings its own page. A surface may own the *whole* row instead of its body (github does, because a record, a list and a body of prose are not columns of one table), which is what `dedicatedRowOf` short-circuits in `Chat.tsx` before the shared tool row is built. A guardrails block is registered with `app.log.block` rather than as a row surface because it lands on pi's own calls as well, and it is drawn last: the reason a call has no answer is the answer.

**The graph stays a star.** A plugin imports `core`, the app's own shared layer (`src/utils`, `src/window`, `src/keys`, `src/keybindings`, `src/fuzzy`, `src/autocomplete`) and its own folder. A plugin-to-plugin edge is a decision, and there is one, named by its reason: `openui → figures` (a program's `Chart` draws the tool's plot from the tool's own geometry, so the two cannot drift). It used to be two — github read the guardrails block because github owns its whole row — and the edge went away when core started drawing blocks over a dedicated row as well. core reading a plugin is not the plugin reaching into the app, so those reads are allowed, but they are the app's own coupling (33 at the time of writing) and the number should only shrink. Cross-plugin imports keep naming the file they come from — a manifest is not a barrel.

A namespace is a folder inside a kind: the agent bridge is `core/lib/agent`, the composer's layout and mode logic is `core/lib/composer`, the DuckDuckGo engine is `web-search/lib/duckduckgo`, the OpenUI component library is `openui/components/library`. A tool is one file per tool, named after the tool: `interaction/tools/askUser.ts` is `ask-user`, `web-search/tools/webSearch.ts` is `search-duckduckgo`, `guardrails/tools/guardrailsTest.ts` is `guardrails-test`, `vcs/tools/vcsLog.ts` is `vcs-log` — the file is camelCase, the tool name it registers is kebab. A plugin that registers no agent tool has no `tools/`.

### Imports: no barrels

Nothing under `src/plugins/` re-exports a folder, and there is no `index.ts` in any plugin or namespace. Every import names the file it comes from: `../../core/lib/ui/theme`, `../../lib/composer/panelHeight`, `../../../interaction/tools/askUser`. Crossing into another plugin means naming that plugin's file — `core/lib/agent/agentService.ts` registers the ask tool by importing `../../../interaction/tools/askUser`, and `core/lib/project/projectSummary.ts` reads jj through `../../../vcs/lib/repo`.

Adding a file means adding its path at each consumer; there is no public surface to keep in sync, and moving a file updates only its own consumers.

### Naming

- a component file is PascalCase and matches the component it exports (`vcs/components/ChangesPanel.tsx` exports `ChangesPanel`). The one exception is a namespace of component _definitions_ rather than components: `openui/components/library/layout.tsx` holds the `Stack`, `Row` and `Grid` definitions of one area of the language and `registry.ts` registers them — the area is the unit there, not one component
- a hook file is `useThing.ts` and lives in its plugin's `hooks/`, in the plugin that owns the thing (`useProjectSummary` in `core/hooks`, `useChangesPanel` in `vcs/hooks`)
- a namespace keeps its key hints in `shortcuts.ts`, and a plugin keeps what the whole plugin shares in `types.ts` and `constants.ts`
- when two modules in one namespace want the same name, the name is the thing that is wrong: the changes panel's state hook returns `ChangesPanelState` so the `ChangesPanel` component owns the name, and the composer counts rows in a height with `composerPanelRowsForHeight` so the panel's own `composerPanelRows` owns its name

## Tests

Three kinds of test, one command. `bun run test` (`bun test`) runs all of them: about 180 tests across 28 files, five minutes, almost all of it in the UI suites, which open a real window.

- `bun run test` — a plugin's logic tests sit beside the file they grade (`lib/read.test.ts`), and they take the seam, not the network: a page read is graded with its loader handed in. The suites in `test/` grade what the app draws.
- `bun run typecheck` covers `test/` as well as `src/`: a stage that stops matching the app's own props is a test that quietly grades nothing.

```
test/
├── harness.tsx      the only thing that opens a window: a headless gpuix test root, the app's providers, the settle loop
├── scenes.test.ts   the scene fixtures graded against themselves
├── chatSource.ts    the session and session-list stubs every scene hands the app
├── stage/           log.tsx (the log alone) · composer.tsx (the composer band alone) · window.tsx (the whole screen)
├── fixtures/        scenes/ — one transcript per feature — plus turn.ts, tool.ts, stage.ts, repo.ts, projects.ts, media.ts, …
└── ui/              one file per surface: what the app actually drew
```

**A UI test paints, and reads the paint.** `stage(<Component/>)` (`test/harness.tsx`) opens an offscreen gpuix window (1280×800 unless the test asks otherwise), renders inside the app's own providers, and pumps frames until the tree stops changing — a virtual list measuring its rows is not cut short, a component that renders in one pass is not waited on. What comes back is the screen: `says`/`words`/`painted` for text, `inkOf`/`boundsOf`/`every` for elements with the x, y and width they were laid out at, `clickAt`/`press` for input, `shot` for a PNG. So a test asserts what a reader sees rather than what a function returned: that a header's chips do not restate its line, that a panel row is one line and not two, that the guardrails block naming why a call stopped stands **under** the row it stopped, that the hint line prints only the keys the panel actually takes, and that a keystroke lands on the row under the cursor. No suite asserts on a snapshot file — an assertion that reads the tree says in its own words why it matters.

**The stage is the app's wiring, minus what the surface does not read.** `stage/composer.tsx` builds every open panel's state through that surface's own `use` in host registration order, and routes a pick through `pickComposerRow` — the same routing `useChatComposer` runs — so arming a guardrail domain, completing a path with Tab, and a panel closing on the choice it was opened for are the app's behaviour, not a stub's. `stage/window.tsx` renders `ChatApp` itself, so the frame (the header naming the folder and its bookmark, the log, the composer band, the status bar) is graded as one thing. `stage/log.tsx` draws the log with the project and repo sources staged, which is where the row-level suites live.

**What is graded where:** `logRows` the shared tool row — one header, its counts, no card restating it; `codemodeRows` pi's three blocks in pi's order; `webRows`, `documentsRows`, `qualityRows`, `githubRows`, `figuresRows`, `diagramRows`, `planningRows`, `generativeUiRows` one plugin's rows each; `guardrailsRows` the block over a stopped call; `snapcompactRows` a span kept as pictures; `sessionStatus` the bar's figures, settled and in flight; `window` the frame; `composerPanels` and `panels` the composer's lists, their keys and their picks; `pictures` the viewer; `questions` the ask panel and the row that waits for it.

**A scene is one conversation.** Every fixture in `test/fixtures/scenes` is the evidence one suite argues from: its own prompts, its own tool calls, its own answer. `test/scenes.test.ts` grades the fixtures against themselves — no two scenes share a transcript or an opening question (`photo-strip` is the hero, and appears twice on purpose: in the log, and as another session's preview); every row is named and no id repeats within a scene; every stamp sits inside one session's span, so the bar's span and rate are figures about a real sitting rather than about 1970 or an hour typed as milliseconds; a row's own end stands after its own start; and `clockOf(items)` pins the moment a scene is read at — one and a half seconds past its last row — so an elapsed figure never moves between runs. A scene that shows a list read off disk stages its own store: `fixtures/projects.ts` writes pi's own shape into the temp dir with ages sitting clear of the bucket the panel prints, and names it with `MU_PROJECTS_STORE`, which the projects plugin is the only reader of.

**One window at a time, and always put away.** `releaseAll()` in `afterEach` closes every screen a test painted — a GPU window left standing across a suite is a leak no reader can see from the test that caused it. The picture viewer and the ask panel are window state rather than a scene's, so a suite that opens one closes it before it returns, and the guardrails suite that flips a domain's switch flips it back.

**The README's pictures are painted by the suite, not by a capture step.** `test/ui/screens.test.tsx` renders one whole window per README heading — the log, a panel open over the composer, a picture opened over the page, a scheme picked — and writes each frame to `docs/screens/<screen>.png`; the README is one heading and one image per screen, and nothing else. The same test that wrote the frame fails if it is not a PNG, is not the window size it claims, is under 30 KB (a solid rectangle compresses to a couple), or fingerprints identically to another screen — which is how one transcript with a different panel bolted on used to end up as two README images. A final test in that file checks the README against the run: every image it shows was written this run, and every frame written this run is shown. A stale PNG is therefore not a housekeeping problem: the gallery is regenerated by `bun test` or it is wrong in the same run that says so. (`docs/screens/*.png` is the one `!`-exception in `.gitignore` for a reason.)

**The UI suites need a binding that carries the test renderer.** They open a real offscreen window through `@gpuix/native`; a build without `test-support` answers `hasTestGpuixRenderer() === false`, there is nothing to paint, and the suite fails to render rather than failing an assertion. `bun run build` in `~/Projects/knoopx/gpuix/packages/native` (napi `--release --features test-support`) is the fix, in the artifact, once. Nothing about the UI suites needs a compositor, and no story or capture step maps a window: the render is in-process, in the same process `bun test` already started.

## Notes

- Path completion lives in `core/lib/composer/pathCompletion.ts`: the draft's trailing path token (`~`, `~/x`, `/x`, `./x`, `../x`, `@x`, anything with a `/`) is listed as a shell lists it, and the completion panel's query **is** the draft — `isCompletionMode` — so typing keeps editing the draft and Tab takes the highlighted path, a directory keeping the panel open. Tab is `editor.autocomplete`, handled in `composer/keyRouter.ts` with the `cycle` flag so the window listener never takes a completion twice. **Tab completes, Enter commits**: `pickActive(intent)` carries a `PickIntent` (`lib/composer/mode.ts`) through `ComposerPanelSpec.onPick` into `panelActions.pickPanelRow`, and path completion is the only panel that reads it — Enter on a folder writes the path and dismisses the panel, Tab keeps completing inside it, and a row's mouse click completes exactly as Tab does. **A panel is a choice, never a send**: `panelListKeys`'s `onEnter` is that commit and `ComposerField.onSubmit` picks whenever a panel is open, so path completion can never submit the draft to the conversation. With no name to take, Enter is inert; Escape closes the suggestions and leaves the characters typed, and Enter in the draft then sends them. `pathCompletionShortcuts` prints Tab's `complete` beside Enter's `use`.
- There is no DOM. Style objects are `StyleDesc` values and layout is flex; `adwaita-gpuix` owns theme tokens, and colour helpers live in `core/lib/ui/theme.ts` so a component never hand-mixes a hex.
- No component writes a bare number in a style. `core/lib/ui/tokens.ts` is the one answer to how big, how much space, what leading and what weight, and it defers to adwaita's scale where that scale already owns the value: `ROW_HEIGHT` is the height of every one-line row (the tree, a change feed, a picker), `monoColumn(t, chars)` _budgets_ a column of monospace text and `monoTextWidth(t, chars)` measures what that text actually prints (`idColumn(t)` is the log's own column, budgeted), and `figureGap(t)` is the one role-gap the scale cannot name — the air between the figures a row trails, which five files used each to spell as `t.space.sm` on their own; `lineBox(t, role)`/`codeLineBox(t)` are the line boxes of text roles (`leadingOf` for a caller that sets a ratio), `emphasisWeight(t)`/`titleWeight(t)`/`plainWeight(t)` are the only weights, and `titleWeight` is semibold, never bold — a heading's size and colour are what put it above the text under it, and a heavy face at a display size is a headline shouting for the reason it never needs (openui's display-size figure takes the same weight); `MARKER_GLYPH`/`INLINE_GLYPH`/`STATE_GLYPH`/`ACTION_GLYPH` are the marks a row draws (`STATE_GLYPH` is the log's mark — a header glyph, a running spinner, a note's icon — and `MARK_HANG` how far it hangs into the page inset), `HAIRLINE` is every rule and edge, and `elevatedShadow()` in `theme.ts` is the one drop over the log, from `ELEVATION`. A plugin's own sizes stay named in its own file when nothing else asks for them (`MAX_ROWS`, `PANE_GROW`); what must not happen is two files spelling the same number differently. Secondary text is `mutedText(t)` — a call site never reads `t.color.text.dim`.
- The transcript page inset (`PAGE_INSET` in `core/lib/ui/transcriptLayout.ts`) is one constant imported everywhere; the adwaita tool-header glyph hangs 24px into it, so the inset stays at 56. The gutter of marks runs the whole height of the window: a running session is a `STATE_GLYPH` spinner hung the same `MARK_HANG` beside the composer box (`ChatComposerSlot`), not a line of prose at the end of the log. That mark is one component, `core/components/StateSpinner.tsx`, and it turns pi's own frames — the ten braille cells of pi's `Loader` (`DEFAULT_FRAMES`), one every 80ms (`DEFAULT_INTERVAL_MS`), in the accent tone — so a running session looks the same here as in the terminal; adwaita's ring `Spinner` is not used anywhere in mu, and the one place it would reach the screen unasked is a running tool header's trailing mark, so `ToolExecution` hands adwaita's `ToolHeader` a `spinnerSlot` of `StateSpinner` and the header keeps only its settled check icon (`spinnerSlot` is the library's own escape: `StatusGlyph` draws whatever the app gives it while it runs, and its icon when it does not); the cell is set in the mono family because that is the family with braille coverage, and `STATE_GLYPH` is adwaita's `GUTTER_GLYPH`, so a header's trailing column does not move when the mark changes — there is no "Working" row and no loader in the transcript. The box keeps the exact x and width it had a moment before because the mark's row pays back the width the hang takes (`MARK_HANG - STATE_GLYPH` of margin), and the mark stands in that row rather than inside the composer's own root, whose fill clips its children.
- The log is a two-column grid and `core/lib/ui/toolRows.ts` owns it: **text** of every row — a header title, an answer's caption, a preview line, a system row — starts at `PAGE_INSET`, and every **mark** hangs `MARK_HANG` to its left, in `STATE_GLYPH`, because adwaita's `ToolHeader` puts its glyph there (`GUTTER_GLYPH`/`GUTTER_GLYPH_HANG`, neither exported) and nothing else in the log gets to pick a second column. So `toolColumn`/`toolGapColumn` open with `paddingLeft: 0` (a column that padded its own left edge indented every body line away from the head it answers), a row-leading icon takes `style={toolMark}` (`toolMarkIn(padding)` inside a column that really does pad), and a lone note is wrapped in `toolBodyStack` rather than returned bare. A plugin never hand-rolls an icon-plus-caption line: `ToolStateLine` (`ToolStateNote`/`ToolStatusNote`) and `ToolCaptionLine` are the only two, and they take `toolText(t)`, which puts a log line on `lineBox(t, "caption")` leading while `toolLine` keeps the row at least that tall — otherwise the rows of an answer sit tighter than the prose above them.
- **A panel closes on the choice it was opened for.** The jump-back tree's Enter goes through its own `wideKey` (`useSessionTree.onKey`) into `useChatPanels.jumpTree`, which navigates and sets `draftMode()` in the same breath: a wide panel draws no draft field (`WIDE_SLOTS`), and a jump back over a user node writes that node's text into the composer, so a panel left open would hide the very draft the jump handed back. The guardrails panel is the deliberate exception — arming is a switch, so its row stays put — and the two repo panels keep their own keys and their own writes. A panel answering a pick of its own is handed `close()` beside `toast` (`PanelPickActions`), which is how the projects panel puts itself away once the window it opened is the one to type into, while guardrails keeps its band.
- **The project list is mu's own session store, not a folder scan.** pi files every session under `<agent dir>/sessions/<folder for the cwd>/*.jsonl`, so the parent dir of a session file is one working directory somebody has already worked in: `projects/lib/projectStore.ts` walks those folders once per window (a `readdir` and a `stat` each, never a transcript body) and takes the path from the `cwd` in the first line of the folder's newest session — the encoded folder name is only a safe spelling of a path (`/` and `-` both become `-`) and is the fallback when that header cannot be read. Two folders spelling one path are one project with both histories; a path the disk no longer holds is dropped. `root` and `exists` are the parameters the tests grade, and `bun test` over that plugin never touches `~/.pi`.
- **A mu window _is_ a working directory.** The agent session, the file panel, the repo panels and every relative path in the log hang off the folder the window was started in, so switching project is a new window at the other path (`src/window/newWindow.ts`'s `spawnWindowIn`, which reuses `appLaunch()` and answers on the child's own `spawn` event), never a repoint under a running conversation.
- **One delete key, and the panel says what its row is.** `composer.deleteRow` (Delete) is matched once in `composer/keyRouter.ts` and answered by `composer/panelActions.ts:deletePanelRow`, which reads the open panel's target; `composer/shortcuts.ts` keeps the one list of panels that can delete (`DELETABLE_PANELS`) and `panelShortcuts` prints the hint for exactly those, so a hint a panel does not print is a key that panel does not take. The session panel hands its row to pi's session store; the file panel hands its row to `lib/files/deleteFile.ts`, which takes a name that stays inside the folder and refuses a folder or a name that walks out of it. `lib/files/` is the file panel's whole read: `fileList.ts` walks the project once per folder, `fileIcons.ts` names the row, `filePreview.ts` reads the pane, `projectPath.ts` is the one read of what a row may point at (inside the folder, not the folder, a file) that both a delete and an open run through, and `hooks/useFileList.ts` drops the walk when a delete lands, so the row that just went cannot sit in the list previewing nothing.
- **A file row opens two ways, and the words are the same in every file pane: `o` hands it to the desktop's default app, `e` to the user's editor.** The Files panel (`ctrl+P`), the changes panel's files pane and the op log's file pane all answer both, so one letter means one program wherever a file row is under the cursor; an operation's file that the operation took out of the tree is refused as already gone rather than opened. In the Files panel both are bare letters, so unlike Delete they are keys the panel would otherwise type into its filter: `keyRouter.ts` takes them in `handlePanelKey` _before_ the character branch (`panelLetterKey`), and only a panel in `OPENABLE_PANELS` hands an `onOpen`/`onEdit`, so no other panel loses a letter to a command — and `panelShortcuts` prints the `open` and `edit` chips for exactly the panels that take them. Two letters is the whole budget there, because that panel's filter is the draft; the repo panels open their filter with `/` and could take more, and do not need to. `core/lib/files/openFile.ts` is the one place a file is handed out: `openFileInEditor` spawns `$EDITOR` (falling back to `vi`) and `openFileInDefaultApp` runs `xdg-open`, falling back to `open`; both go through `spawnProgram` in `src/utils/launcher.ts` — detached, stdio ignored, `withoutMuLoaderEnv`, and an answer that waits for the child's own `spawn` event so a program that is not on the road is reported instead of promised — and both refuse a name that is not a file inside the folder (`projectFile`) before anything starts. `openNotice(result, name, target)` words both halves and names the program, because a reader has to tell the two keys apart from the toast alone. The panel stays open and the cursor stays put, because the list is how the next file is picked. The repo panels share one writer, `vcs/lib/fileOpen.ts`'s `openPanelFile`, which reads the path against `findWorkspaceRoot()`; the Files panel's own pair is `useFileList`'s `open`/`edit` through `panelActions.openPanelRow`/`editPanelRow`. `src/window/openLink.ts`'s `openExternal` is a link, not a file, but it runs the same launcher chain, so a desktop with neither launcher says so in one wording.
- Every panel in the composer slot — the draft's list panels, the question panel, the changes panel, the history panel — is framed by `core/lib/composer/chrome.ts`, and nothing else states their padding. `panelBox(t, tone)` is the band, and it pads itself by one unit — `panelPad` (`space.sm`) on **all four** sides, so `panelPageInset` and `panelPadY` are the same number and a panel breathes equally top, left, bottom and right. Everything the panel says then stands `panelInset` further in, so the ink column sits at twice the band's breathing from the left and right and one measure from the top and bottom — a 1x2 width-to-height ratio, an equal band being its degenerate case, and the reason a second padding number in a panel is a bug rather than a taste (a chip or an inline mark is not a band and keeps its own measure). The field, the list, the hints line and the notes all stand in that one column, and a row's hover band simply runs `panelInset` wider than its text. `panelChrome(t)` owns the panes (`listPane`, `flexPane`, `widePane`, `previewPane`, `previewCode`), the rules (`ruleV`/`ruleH` take the colour a panel's tone asks for, since tone is the one thing chrome cannot know), the `rowSlot` a virtual list stands one row in, and the `emptyPane`; `ChangesPanel`, `SessionTreePanel` and `AskComposer` all read it rather than restating it. `panelHeight.ts` does the arithmetic over those same numbers — `panelChromeHeight(t, slots)` charges a panel only for the slots it draws, and the wide panels draw no draft field — so a padding moved in `chrome.ts` moves a row budget with it. `lib/composer/field.ts` is the one answer for the draft every panel types into: `panelInset` of left padding and `fieldPadY` of breathing (floored, so a one-row field plus its pad stays inside `ROW_HEIGHT`), whether it holds one line (`composerFieldLineStyle`) or grows with its text (`composerFieldBox`). `paneInk(t)` is the padding of the ink a pane holds that is _not_ a row — the preview pane (`previewPane` pads itself with it, so adwaita's `DiffPanel`, mu's `previewCode`, an image tile's caption and a pane note all land under the file paths above them), the question panel's title, context, detail and hint row. `panelGap` is the air between one panel's slots and `paneGap`/`ruleGap` are exactly twice it, so nothing writes `t.space.md` between two panes.
- **A panel row is one line, and where its name lives is a column.** An option row may carry `place` — the folder a name sits in, not the whole path printed a second time under itself — and `composerPanelShapeOf` gives every row of a list that column, measured across the list and fluid when the list has one, so names line up, places line up, and the projects store windows twice the rows it did when the second line spent itself restating the name (`core/components/composer/panelTable.tsx`, mirrored by the standalone `ComposerOptionRow` the repo panels draw). Its figures ride as marked columns of their own, and a mark means one noun across the app: `chat` is the sessions waiting in a folder, `history` is when it was last worked in, and a clock on a count is a figure read wrong, because the row's real time stands at its end.
- The figures the status bar keeps in view are the **session's own, read live**. `core/lib/agent/turnStats.ts` is the only place they are computed: one `scan` over the log's rows answers what the provider has reported, what is still streaming, and when the rows last did something, and `conversationStats(items, clock, sessionStart?)` folds that into the bar's turns, tokens, span and rate — a span from the log's first timestamped row to its last activity, never from when the window opened, so a resumed session says its own length and a new one starts at zero. `useRunningClock(running)` (`core/hooks/`) ticks `now` while a run is in flight and `Chat.tsx` hands it to `useTranscriptView` as a `SessionClock`, so elapsed time keeps moving through the seconds a turn spends in its tools, where nothing streams. A decode in flight has no usage to read — a provider answers at the end of a message — so its tokens are _estimated_ at four characters each, the estimate pi's own compaction makes, and the row carries the timing for it: an assistant row keeps `startTs` from `message_start` and a tool row `endTs` from its result, so the live figure counts streamed prose, reasoning, and the arguments of the calls the streaming message is still writing, and never the arguments of a call that already ran (its tokens landed in a usage figure). `ConversationStats.live` says the rate is being measured now, and the bolt segment stands in the accent while it is. Turn footers stay settled-only: `turnStatsById` answers a turn's figures with no estimate, because the moving numbers belong to the bar. `ChatAppProps.now` pins the clock a scene is read at — `test/fixtures/turn.ts`'s `clockOf(items)` puts that moment a moment and a half past the scene's last row — so the bar's elapsed figures are the same figures on every run.
- Images go through pi's own pipeline and `core/lib/agent/settings.ts` overrides nothing in the `SettingsManager` it builds for `createAgentSessionServices`: an image is converted to a supported format, EXIF-corrected and downscaled under the provider's inline limit, and the note pi adds tells the model the coordinate scale. Every resize path reads `photon_rs_bg.wasm` **from disk** — the resize worker cannot start from an embedded bundle, and photon's glue asks for the build machine's path — so a `bun build --compile` binary resizes only if the package installs that wasm where pi's loader already looks, beside the executable (`flake.nix` puts it in `$out/lib/`). Without it `resizeImage` returns null and every image answers "[Image omitted: could not be resized below the inline image size limit]", at any size. There is no `images.autoResize` override: an in-memory `applyOverrides` is wiped by pi's `SettingsManager.reload()` during resource loading, so it was inert anyway.
- **A picture in the log is a thumbnail, and clicking it opens the real one.** `core/lib/ui/imageViewer.ts` holds the view outside React — which picture, and the group it was opened with (the images of one message, the two sides of one change) — `core/components/ImageViewer.tsx` draws it over the whole window on a ground of its own (`PICTURE_*` in `core/lib/ui/theme.ts`, the only colours in the app that ignore the scheme, because a near-black ground needs light ink to say what the picture is called), and `core/components/ZoomImage.tsx` is the one click: every picture the log draws goes through it — a read's tile, a sent message's thumbs, a change's two sides, a diagram, the files panel's preview — so the hover badge and the behaviour cannot drift per row. Escape, a click beside the picture, or its close mark puts it away; the arrows walk a group, and the keys are one list in the store (`viewerHints`) so the hint line cannot name a key the picture does not take or hide one it does. **The picture is the window's one modal**: `composerGlobalKey`, `composerFieldKey` and `composerListKey` return before routing while `viewerHoldsKeys()`, and `AskComposer` asks the same question, so Escape puts the picture away rather than opening the history panel, aborting a run, or answering a question that is not on screen.
- **A wrapper's environment is mu's, never a child's.** The Nix wrapper sets `NAPI_RS_NATIVE_LIBRARY_PATH` (gpuix-native's `.node` under `$out/lib`) and `NODE_PATH` (`$out/lib/node_modules`, where QuickJS's wasm ships) because a `bun build --compile` executable finds neither on its own, and a wrapper cannot give one process an environment of its own. So the app retires them itself, in `core/lib/utils/loaderEnv.ts`: `retireNativeLibraryEnv()` runs in `app.tsx`'s entry body — after the entry's own imports have loaded the GPU binding, which is the only thing the variable is ever for — and drops it from `process.env`, the environment pi's bash tool and every other spawn inherits; `withoutMuLoaderEnv()` strips both at the spawns mu owns that are not mu (the pty shell, the analyser CLI, the editor), and `withMuLoaderEnv()` hands them back to a child mu window. That is not tidiness: every napi-rs generated loader — gpuix-native's own `index.js`, and the same generated file in `@tailwindcss/oxide`, tree-sitter, oxc — reads that variable before it looks anywhere else, `require`s what it names, and never checks what came back, so a project built inside mu loads gpuix-native as its own binding and dies somewhere else on an export that is undefined. `NODE_PATH` cannot be retired the same way, because pi resolves `quickjs-wasi/quickjs.wasm` through it lazily at the first codemode call; it is stripped per spawn instead.
- Anything an embedded dependency reads with `fs` at runtime, rather than through an `import`, has to ship as a file: `photon_rs_bg.wasm` beside `$out/lib/mu`, and QuickJS's `quickjs.wasm` under `$out/lib/node_modules/quickjs-wasi/` with the wrapper setting `NODE_PATH` there, because inside a compiled binary `require.resolve` searches `NODE_PATH` and the process cwd and never the executable's directory. Guardrails' grammars are the opposite case — `with { type: "file" }` imports, so `bun build --compile` embeds them.
- codemode's worker is a compile entrypoint, not just a module: in a bun-compiled binary pi spawns it at the literal path `./src/extensions/codemode/worker.ts`, so mu keeps that one-line shim at exactly that path (the path is pi's, and moving it breaks codemode) and `flake.nix` passes it as a second entrypoint to `bun build --compile`. That is why `@earendil-works/pi-codemode` is a direct dependency.
